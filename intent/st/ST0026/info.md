# ST0026: arngz: named window arrangements (desks) discovered and applied across displays and spaces

## Objective

A new utility, `arngz` ("arranges"), that records and restores named window arrangements on macOS. An arrangement is a **desk**: one or more uniquely identified **displays**, each holding one or more **spaces** (named by text or ordinal), each knowing a set of **apps**, each app carrying one preferred **layout** on the screen in Hammerspoon-style logical grid coordinates.

```
[desk] -1-n- [display] -1-n- [space] -1-n- [app] -1-1- [layout]
```

A desk is declared in a simple config file (format to be decided). The two main uses:

- **apply**: `utilz arngz zeop1` puts every app in the desk on its preferred space at its preferred grid position, on this machine's displays.
- **discover**: read the apps, spaces and positions laid out right now on the displays attached right now, and save or update them as a named desk in arngz's local config.

With the usual command-line verbs around them (list, show, delete, init, doctor, dry run). The tool is for hv's own machines: it must fix macOS's habit of putting windows on arbitrary spaces, and it works with Hammerspoon or an equivalent engine. Implementation language (Rust, Swift, or shell over Hammerspoon's Lua) is a design decision, and "super simple to use" is the criterion.

## Context

Asked by hv on 16 Oct 2026 in a rubber-duck session with vc. The thread is created and started ahead of the design: hv wants a review of the ask and of what macOS makes possible first, and the design is elaborated once the ask is ironed out. macOS has no public API for Spaces, so the design's first job is to settle which engine carries the private-API risk (Hammerspoon's `hs.spaces` is the candidate) and to measure, on this machine's macOS (Darwin 27), whether moving a window to another space still works before anything is built on it.
