## What

`AT04` in `opt/prez/crate/test/acceptance.sh` fails on hv's machine under Chrome 155.0.8059.85, on two of its 52 runtime-probe checks:

```
FAIL fullscreen_entered=null want=HTML
FAIL fullscreen_fills=false want=true
```

So `utilz test prez` is red locally (1 of 6 suites), whatever the change under test.

## Evidence

- Found by cc on 16 Oct 2026 while running `utilz test prez` for issue 0065.
- Fails on three consecutive runs of `test/acceptance.sh AT04` alone, so it is not the port-race flake that 0063 fixed.
- Fails identically on HEAD `13552bc`, built in a detached worktree with its own `CARGO_TARGET_DIR`, before 0065's change. `demo.md`, which AT04 builds, compiles byte-identical before and after 0065, so 0065 cannot reach it.
- CI run 38851732238 on `faa886d` passed, with the Chrome on the Linux runner image. That points at this machine's Chrome version rather than prez's runtime, but nothing here has measured the cause yet.

## Cause, measured (cc, 16 Oct 2026)

prez is not at fault. Its `f` handler calls `document.documentElement.requestFullscreen()` from the keydown with the keypress's activation live, and **a visible Chrome 155 window honours it**: driven over CDP with the same trusted key, the promise resolves and `document.fullscreenElement` is `HTML`. What changed is the browser's headless mode:

| Chrome 155.0.8059.85, macOS                    | Fullscreen from prez's `f` key           |
| ---------------------------------------------- | ---------------------------------------- |
| a visible window                               | granted                                  |
| headless                                       | `TypeError: not granted`, activation live |
| headless, requested from a trusted mouse click | granted                                  |
| headless, requested via `Runtime.evaluate` with `userGesture` | granted                     |

Ruled out: the `char` event (sending only keydown and keyup refuses the same way), focus (`document.hasFocus()` is true, and focus emulation changes nothing), and the permission (Chrome 155 accepts a CDP grant for `fullscreen` only with `allowWithoutGesture: true`, which would bypass the very gesture AT04 proves). CI's Linux headless Chrome still honours the key: run 38851732238 passed all four fullscreen checks. Separately, headless macOS reports a fixed 800x600 screen whatever `--window-size` says, so `fullscreen_fills` could not pass there either; `--screen-info` fixes that and nothing else.

## Resolution (hv's ruling, 16 Oct 2026)

AT04's fullscreen claim is split in two:

- **prez's half, checked on every platform.** Before the press, the probe wraps `requestFullscreen` and passes the call through untouched. It then checks that `f` called it on `HTML` with activation live (`fullscreen_requested`, `fullscreen_request_had_activation`). A control artifact with the call removed turns both red.
- **The browser's half, `n/a` on macOS by `uname`**, under hv's 8 Sep ruling: fullscreen entered, fills the screen, and toggles out. The Linux leg runs it, so it stays covered. A control run without the gate still fails here exactly as before.

AT04 also prints the browser's version, so the next change of this kind shows up in the log.
