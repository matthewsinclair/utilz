## What

`artifact::path::on_path` (`opt/prez/crate/crates/artifact/src/path.rs:12`) takes the first file called `name` in a directory on PATH, by `is_file()` alone. A file there that is not executable counts as found, where the shell's own lookup passes over it and goes on to the next directory. The browser finder's absolute candidates (`browser.rs`'s `is_runnable`, `:78`) are `is_file()` alone too.

Its callers are the browser finder's PATH names (`browser.rs:64`), showreel `video`'s ffmpeg and ffprobe (`crates/showreel/src/video.rs:95`, `:221`), and from 0083's prez part `present`'s fallback opener. In each, a non-executable file ahead of a good one is taken. The run then fails at the launch, as "could not launch '<path>': Permission denied", with a remedy for a different case, and the finder's probe list and the good command later on PATH are both lost. Loud, not silent, but it points the user away from the cause.

critic-rust saw it in its review of 0083's prez part (19 Oct 2026). vc ruled it a shared-helper defect, outside 0083: cc's, XS, fixed after 0087, design first.

## Fix, for the design to settle

`on_path`, and the finder's `is_runnable`, keep only a regular file with an execute bit, as PATH lookup does. The test is the helper's own, through `find_in` with a PATH of the test's making, since the crate's tests empty the process's PATH (`path.rs:17`): a non-executable file ahead of an executable one, and the executable one wins. On a platform with no execute bit the check is the file alone, as now. Size: XS.
