## What

hv, 22 Oct 2026, in utilz-ic's session, on why menuz and its peers could not move to Xcode 27.x everywhere, and of arca_swift: "Its new and only used by me. Push on and do it. Then fail forward."

menuz's Xcode floor is Xcode 26 (`project.yml`'s `xcodeVersion: "26.0"`, issue 0073), and tests.yml's menuz-app job builds and tests the app on macos-26's default Xcode, 26.6. Nothing menuz ships is built that way. 2.14.1's `Menuz.app` was built here with Xcode 27.1 on the macOS 27 SDK, for macOS 26.0, and a Homebrew install never builds: `menuz install` fetches that signed asset. So CI checks a toolchain nothing ships with, and the local twin of its job, which hv's ready-to-cut rule asks for, runs on a different Xcode from CI's.

## Fix

1. The menuz-app job builds and tests on Xcode 27.1, the Xcode the release asset is built with, named rather than taken as an image's default, which moves.
2. menuz's Xcode floor is 27.1, so `menuz doctor` refuses an older Xcode by name, and every restatement says 27.1 or points at `xcodeVersion`.
3. The app still runs on macOS 26: `deploymentTarget` stays 26.0, so the SDK's availability checks still refuse a macOS 27 API used without a check. What goes is a run of menuz's tests on macOS 26, since the `xcode-27` image runs macOS 27, as this Mac does.
4. The first run on the new image is the menuz-app dispatch after hv's push. A red there is fixed forward, on hv's word, and reopens this issue.
