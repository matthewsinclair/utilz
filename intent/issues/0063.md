AT04 ("base runtime in a real browser") failed on the Linux leg of the 2.12.0 tag run because Chrome never accepted a connection on the debugging port the suite told it to use:

    FAIL  chrome never opened its debugging port on 9333
    [TypeError: fetch failed] { [cause]: Error: connect ECONNREFUSED 127.0.0.1:9333 ... }

A CORRECTION TO THIS ISSUE'S FIRST WORDING, which said the port was "unwaited". IT WAS NOT. `wait_for_cdp` (test/lib/harness.sh) already polled for up to 10 seconds, added after this same AT failed on CI on 2026-08-29 when the code used `sleep 2`. Writing "unwaited" was the same error this project keeps finding in its instruments -- a claim wider than what was measured -- and it pointed at a fix that was already in place. What follows is measured.

PROVED FLAKY BY CONSTRUCTION. The release commit 1b8dab1 carries two runs, because a cut pushes the branch and the tag and each triggers the workflow:

- run 35745440211, ref `main`, `Rust (ubuntu-latest)` = SUCCESS
- run 35745443734, ref `2.12.0`, `Rust (ubuntu-latest)` = FAILURE (this AT04)

Identical bytes, identical workflow, opposite outcomes, so the failure is non-deterministic rather than a regression. Corroborating: every `Rust (ubuntu-latest)` job from 2026-09-20 onward before this one is success, and within the SAME failing job AT05, AT06 and AT07 each resolve and launch `/usr/bin/google-chrome` successfully seconds later. Chrome works on that runner.

THE TWO REAL DEFECTS, both fixed.

1. THE PORT WAS A CONSTANT, AND THAT IS THE LIKELIER CAUSE. Every CDP launch across the two black-box suites used a hard-coded port -- 9333, 9350, 9360 to 9363, 9370 to 9372. Anything already holding one makes Chrome fail to bind, and the ONLY symptom is `wait_for_cdp` reaching its ceiling and the caller blaming Chrome's startup. A leftover Chrome from an earlier block of the same run is enough. That is a false diagnosis pointing at the wrong subsystem. `cdp_port` now asks for a port nothing is listening on, at the moment it is needed, and REFUSES rather than falling back to a constant -- a fallback to a fixed port being the exact bug it replaces. All nine call sites use it.

2. THE WAIT WAS SILENT AND SHORT. The ceiling was 10s, chosen on a warm laptop, and on reaching it the refusal said only "chrome never opened its debugging port", which reads as "Chrome is broken" when it usually means "this runner was slower than the ceiling". The ceiling is now a named 30s (`CDP_CEILING`), and `CDP_WAITED` carries the measured wait so every caller's refusal states it.

VERIFIED: `cdp_port` returns a port nothing is listening on; `wait_for_cdp` against a port nobody opens returns 1 and reports `1s (the ceiling)` with the ceiling lowered for the probe; AT04 passes end to end on an ephemeral port, 52 checks.

CONSEQUENCE FOR RELEASES, unchanged and worth keeping on the record: `tools/ci-state` answers with the WORST of every run on a sha (issue 0052, deliberately), so one flaked run of the two made 2.12.0's recorded verdict red while the same commit was green on its other run. That is the reader behaving correctly on bad input.
