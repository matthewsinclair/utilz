AT04 ("base runtime in a real browser: keys, counter, overview, hash, fullscreen") fails intermittently on the Linux leg because Chrome does not open its remote debugging port before the probe connects:

    AT04 -- base runtime in a real browser: keys, counter, overview, hash, fullscreen
    note: browser resolved to /usr/bin/google-chrome
      FAIL  chrome never opened its debugging port on 9333
    [TypeError: fetch failed] { [cause]: Error: connect ECONNREFUSED 127.0.0.1:9333 ... }
      FAIL  the runtime probe reported failures
    AT04: FAIL (2)

PROVED FLAKY BY CONSTRUCTION, WHICH IS THE PART WORTH KEEPING. The release commit 1b8dab1 carries TWO runs, because a cut pushes the branch and the tag and each triggers the workflow. They disagree:

- run 35745440211, ref `main`, `Rust (ubuntu-latest)` = SUCCESS
- run 35745443734, ref `2.12.0`, `Rust (ubuntu-latest)` = FAILURE (this AT04)

Identical bytes, identical workflow, opposite outcomes. No code difference can explain that, so the failure is non-deterministic rather than a regression. Corroborating: every `Rust (ubuntu-latest)` job from 2026-09-20 to 2026-09-22 before this one is success, and within the SAME failing job AT05, AT06 and AT07 each resolve and launch `/usr/bin/google-chrome` successfully seconds later -- AT06 even asserts `prez processes still alive = 0`. So Chrome works on that runner; what fails is AT04's wait for port 9333.

THE DEFECT IS THE WAIT, NOT THE BROWSER. AT04 connects to a FIXED debugging port and the probe fetches before Chrome is listening. Two things to fix, and the second matters more than the first:

1. Wait for the port rather than assume it. Poll `127.0.0.1:9333` until it accepts or a named deadline passes, and on timeout say how long it waited. A bare ECONNREFUSED from `fetch` is a stack trace, not a diagnosis.
2. A FIXED port is itself a hazard. 9333 is hard-coded, so two suites, a leftover Chrome from an earlier AT, or anything else on the runner holding that port produces exactly this symptom and blames Chrome's startup. Take an ephemeral port and read the one Chrome reports, as the CDP code elsewhere in this crate does.

CONSEQUENCE FOR RELEASES, which is why this is not cosmetic. `tools/ci-state` answers with the WORST of every run on a sha (issue 0052, deliberately), so one flaked run of the two makes the release's verdict red:

    failed	failure: 35745443734 of 2 runs on this commit

That is the reader behaving correctly on bad input. 2.12.0 is tagged, pushed to both remotes and has its release object; its CI verdict is red solely because of this flake, and the same commit is green on its other run.

NOT A RELEASE BLOCKER and not a regression. Filed after the tag.
