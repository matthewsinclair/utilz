## What

`lua_bin()` in `opt/utilz/test/test_helper.bash` picks the interpreter the project's Lua suites run under by testing each candidate with `command -v`:

```
for b in lua5.4 lua luajit; do
  if command -v "$b" >/dev/null 2>&1; then
    command -v "$b"
    return 0
  fi
done
```

`command -v` names a file that is present but **not executable**, which this project has already been bitten by and recorded: a non-executable hit is reported as found, and the caller then runs it and gets exit 126 or 127, which reads as the test failing rather than as the interpreter never having run.

## Measured

Found by `utilz-dc` on 10 Nov 2026 while moving this function out of `opt/arngz/test/arngz.bats` into the shared helper for ST0033, and reported to `utilz-vc`. dc deliberately kept the body identical, so the move is provable by diff, rather than smuggling a hardening into a move. That was the right call and it is why this is a separate issue.

Two suites now depend on this function: `arngz.bats`'s `AT-03.2` for `plan_test.lua`, and `engine.bats`'s `AT-01.2` for `engine_test.lua`.

## Fix

Test that the candidate is executable, not merely present, and keep the existing contract that no interpreter is a failure rather than a skip. Read 126 and 127 from a candidate as "never ran" rather than as a failing suite.

`opt/utilz/test/test_helper.bash` already has an uncommitted change in the tree from the move, so this fix costs one suite re-run rather than a second.
