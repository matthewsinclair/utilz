## What

`showreel video` records a reel into the next `_out/` slot. `build::run` writes the slot's HTML (`video.rs:107`), the video's name is the HTML's with `.mp4` (`:114-117`, through `deliver::video_of`), and `place` renames the finished partial onto that name (`:206`), which replaces whatever is there. Since 0098 the HTML is created and never replaces a revision, but the video's name comes from the HTML's number alone, and the listing counts HTML files only. So when a revision's HTML has been deleted by hand and its video kept, the next build takes that number again, and the recording replaces the kept video, with nothing said. critic-rust found it reading 0098's candidate v1 on 22 Oct 2026. vc made it cc's own issue for 2.14.2 after 0099 (22 Oct), ruling that a slot's video is placed without replacing and that `-o` overwrites as now.

## Where, by reading (main at `020fd4db`)

- **The slot's video name**: `video.rs:114-117`, the HTML's name with `.mp4`, a slot's one container.
- **Before recording**: the sweep at `:120` (`sweep_partials`) removes what an interrupted run left; nothing checks the video's own name.
- **The placement**: `place` (`:188-217`) renames the partial with `std::fs::rename(partial, video)` (`:206`), which replaces a file at `video`.
- **The slot's HTML**: since 0098, `Stem::write_next` names it and creates it, for `build` and for `video` alike, and nothing it does looks at the slot's video names.

## Design

cc, 22 Oct 2026, at `020fd4db`. Size: S. It lands after 0099 and is built on 0099's landing, which carries 0098's `write_next`. Read and approved by vc, 22 Oct, with one change, folded in: v1 of this design checked the video's name after the build had written the slot's HTML, which would leave a fresh HTML beside the old video, one slot from two builds; the slot is now checked before anything is written, in the one place that names it (point 1).

1. **A slot is checked whole before anything is written.** `Stem::write_next` refuses a counted revision when either of its slot's video names (`VIDEO_EXTENSIONS` through `video_of`) is already taken, before it creates the HTML, through one function, `deliver::refuse_a_taken_name(&Path) -> Result<(), Failure>`, by `std::fs::symlink_metadata`: a name that is free (`NotFound`) goes on; anything at it refuses, naming it, `<video> is already there, so a new build cannot take its slot`, with the remedy `move it aside, or name the output yourself with --out (or video's -o)`; and a check that fails refuses, naming the name. `build` and `video` both write through `write_next`, so the slot's names come from `deliver` alone and neither works them out. A plain `build` refuses too: an HTML beside another build's video would make one slot of two builds, which `prune` would then delete together (AC-03.5). Nothing has been written when it refuses, so nothing is left behind. A fixed name is overwritten each build, its video too, as they always were.
2. **The placement checks again, and never replaces a revision's video.** `Built` says whether its HTML is a counted revision, and `place` is told: that video may not replace; `-o`'s and a fixed name's may, as now. For a revision it checks the name again just before the rename, through point 1's function, and refuses as point 1 does, removing the partial (0096's `remove_partial`). `std::fs::rename` cannot be told not to replace, and a hard link, which would refuse at once, fails on a filesystem without links (FAT, exFAT), so the check is what holds the rule. The window between the check and the rename is not open to another showreel run: since 0098 a second build cannot take the same slot, because its HTML is created and never replaces one. What is left is a writer outside showreel making exactly that name inside the window, stated here and accepted.
3. **`-o` overwrites as now** (vc): an explicit destination is outside the rotation, as `build --out` is.
4. **Red first.** (a) A unit test for point 1's function: a free name passes; a file at the name refuses, naming it, and keeps its bytes; a dangling link at the name refuses too, since it is a name taken; and a name that cannot be checked (its directory at `0600`, listable and not searchable, with 0095's rule for root) refuses, naming it. Red by a one-line mutation each: the taken arm passing, and the error arm passing. (b) A unit test for `write_next`: a counted revision whose slot's video name holds an orphan video refuses, naming it, creates no HTML, and the orphan keeps its bytes. Red by a one-line mutation that skips the slot's check. (c) End to end, as a check in `video.sh`'s AT29 (the slot), which needs Chrome and ffmpeg, so on this Mac: with an orphan video at the next slot's name, `showreel video` refuses before anything is written, no new HTML is left in `_out/`, and the orphan keeps its bytes. Red on main, where the recording replaces it: the candidate's `video.sh` run in main's tree, with its own build, as 0095's R2b ran `acceptance.sh`. Point 2's second check has no test of its own: it needs a recording that worked and a name taken during it, and its words are point 1's.
