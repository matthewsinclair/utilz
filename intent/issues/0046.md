`.github/workflows/tests.yml` runs on every push to `main` and on every pull request, and it has no `concurrency` block, so a run that a newer push has superseded still runs to the end, both macOS legs included.

THE RULING, hv, 2026-09-21, for the fleet (Devbin issue 0108, Devbin vc decision 32): (1) a macOS job runs only on release tags and on demand, in every repository with macOS artefacts, and Ubuntu stays on every push; (2) every repository cancels superseded runs on push, not only the macOS ones.

AT UTILZ, hv, 2026-09-22, directly to cc: half (2) only, and macOS stays on every push. Utilz is public (`gh repo view matthewsinclair/utilz` reads PUBLIC). GitHub charges nothing for its standard hosted runners on a public repository, macOS included, and the minutes behind the ruling were measured across the private repositories only (Devbin 0108). The macOS legs are also Utilz's only bash 3.2 run: the cut's own `test estate` gate runs bats under Homebrew's bash 5 on hv's machine, so macOS on tags alone would put the first 3.2 run after the core has pushed the tag.

THE FIX, in `tests.yml` alone:

- A workflow-level `concurrency` block, its group keyed on the workflow and `github.ref`, with `cancel-in-progress: true`. A newer push to `main` cancels the run on `main` that it supersedes, and a pull request's ref is a group of its own.
- `test-summary` runs on `!cancelled()` instead of `always()`. `always()` is true even in a cancelled run, so once cancelling is routine, every superseded run would start the summary, which exits 1 and reports the cancelled jobs as failed tests. `!cancelled()` still runs it whatever the jobs it needs concluded, which is what `always()` was there for, and skips it only when the run itself was cancelled.
- No tag trigger and no `workflow_dispatch`, so a release push still makes exactly one run on the release commit, and the `--limit 1` in `install_ci_state` (install.sh:674) has one run to read.

`pr-checks.yml` is not touched: it runs on pull requests only, and Utilz commits straight to `main`.

WHAT IT CHANGES DOWNSTREAM: a superseded commit's run now concludes `cancelled`, routinely rather than by hand. `utilz install` and `upgrade` record CI's verdict and never enforce it (install.sh:894-896), so a publish from such a commit records `cancelled`. `tools/ci-state`, the release core's `ci.query`, reads `cancelled` as `failed`. A release commit can only meet that if something lands on `main` between the release push and the core's CI read, which the cut's hold on every write (ST0019 D6) already rules out. `docs/releasing.md` says so.

TESTS: none added. The block is configuration GitHub reads, and the proof is CI's own run on the pushed commit, green. The shape checks that already read `tests.yml` (`opt/utilz/test/common_lib.bats`) must still pass.
