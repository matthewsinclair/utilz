## What

`check_command` in `opt/utilz/lib/common.sh` was `command -v "$1" >/dev/null 2>&1`. bash's `command -v` names a file on PATH that is not executable when nothing executable matches, so `check_command` called a command present when the only file of that name on PATH cannot run. `utilz doctor` checks every utility's command dependencies through it (`dependency_present`), as do `require_command`, the yq and bats checks, and `xtrct` and `pdf2md`'s python3 checks.

## Measured

16 Oct 2026, in a scratch dir: a file `hs` with mode 644 first on PATH and no other `hs`. `command -v hs` exited 0 and printed that path under /bin/bash 3.2.57 and Homebrew bash 5.3.20, and `[[ -x ]]` on it was false. critic-shell's second pass of ST0026 WP-06 (3777de3) found the same quirk in arngz's hs_tool_state, fixed in c654d4f. dc found it in check_command while fixing that.

## Impact

A dependency shadowed by a non-executable file of the same name reads as installed in `utilz doctor`, and the utility then fails when it runs it, exit 126.

## Fix

`p="$(command -v "$1" 2>/dev/null)" && [[ "$p" != /* || -x "$p" ]]`: a path that `command -v` gives must be executable. A builtin or function, which it names without a path, still counts. A new test in `opt/utilz/test/common_lib.bats` puts a mode-644 file first on PATH and asserts failure, then chmods it 755 and asserts success. It was red before the fix under both bashes.
