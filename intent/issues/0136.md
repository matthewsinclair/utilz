## What

`AT-03.2` in `opt/arngz/test/arngz.bats` runs `plan_test.lua` under plain Lua and then asserts its output with `assert_output_contains "0 failed"`. That assertion cannot do the job it looks like it is doing, in two separate ways:

- **A driver that ran no checks at all would pass it.** `plan_test.lua` prints `plan_test: 0 passed, 0 failed` and exits 0 when it runs nothing, so both `assert_success` and a `"0 failed"` match accept a suite that proved nothing.
- **`"0 failed"` is a substring of `"10 failed"`.** A run with ten failures contains the literal the assertion looks for.

Nothing is wrong today: `plan_test.lua` does run arms, and `assert_success` catches a non-zero exit, which a real failure produces. So this is a latent weakness in an assertion, not a live defect. It is the same class as the three arms `critic-shell` found in ST0032's own tests, one of which could not go red at all.

## Measured

Found by `utilz-dc` on 10 Nov 2026 while writing ST0033's driver, and reported to `utilz-vc`. `AT-03.2` belongs to ST0026, which is closed, and its row is green.

The correct shape already exists in the tree, written for exactly this reason: `opt/arngz/test/engine.bats`'s `AT-01.2` arm parses the driver's summary line, requires the line to be present, requires the failures to be none, and requires the count of what ran to be more than none, with neither number written down. That is what this fix should copy.

## Fix

Parse `plan_test.lua`'s summary in `AT-03.2` as `engine.bats` parses `engine_test.lua`'s: require the summary line, require zero failures, and require the passes to be more than zero. No expected count is written down, so the project's no-magic-numbers rule is kept.

`opt/arngz/test/arngz.bats` already has an uncommitted change in the tree from ST0033's `lua_bin` move, so this fix costs one suite re-run rather than a second.
