## What

`AT-03.2` in `opt/arngz/test/arngz.bats` runs `plan_test.lua` under plain Lua and then asserts its output with `assert_output_contains "0 failed"`. That assertion cannot do the job it looks like it is doing, in two separate ways:

- **A driver that ran no checks at all would pass it.** `plan_test.lua` prints `plan_test: 0 passed, 0 failed` and exits 0 when it runs nothing, so both `assert_success` and a `"0 failed"` match accept a suite that proved nothing.
- **`"0 failed"` is a substring of `"10 failed"`.** A run with ten failures contains the literal the assertion looks for.

Nothing is wrong today: `plan_test.lua` does run arms, and `assert_success` catches a non-zero exit, which a real failure produces. So this is a latent weakness in an assertion, not a live defect. It is the same class as the three arms `critic-shell` found in ST0032's own tests, one of which could not go red at all.

## Measured

Found by `utilz-dc` on 10 Nov 2026 while writing ST0033's driver, and reported to `utilz-vc`. `AT-03.2` belongs to ST0026, which is closed, and its row is green.

The correct shape already exists in the tree, written for exactly this reason: `opt/arngz/test/engine.bats`'s `AT-01.2` arm parses the driver's summary line, requires the line to be present, requires the failures to be none, and requires the count of what ran to be more than none, with neither number written down. That is what this fix should copy.

## Fix

Parse `plan_test.lua`'s summary in `AT-03.2` as `engine.bats` parses `engine_test.lua`'s: require the summary line, require zero failures, and require the passes to be more than zero. No expected count is written down, so the project's no-magic-numbers rule is kept.

`opt/arngz/test/arngz.bats` already has an uncommitted change in the tree from ST0033's `lua_bin` move, so this fix costs one suite re-run rather than a second.

## Design

utilz-dc, 10 Nov 2026, every line read in that day's tree. Written before any code, on hv's "go with your recommendations" (utilz-vc decision 98).

### Live and latent, which the What above overstates

The What gives two ways the assertion fails. Only one of them is live.

- **Zero arms is LIVE.** `plan_test.lua` ends in `os.exit(failed == 0 and 0 or 1)`, so a run that executes no checks prints `plan_test: 0 passed, 0 failed` and exits 0. `assert_success` accepts it, and so does a `"0 failed"` match. Nothing in the arm can tell a suite that proved everything from one that proved nothing.
- **The `"10 failed"` substring is LATENT and cannot bite today.** The same `os.exit` line means exit 0 if and only if no check failed, so under exit 0 the summary always reads `N passed, 0 failed`. A run with ten failures exits 1, and `assert_success` rejects it before the substring is ever consulted. The trap would bite only if a future `plan_test.lua` stopped exiting nonzero on failure. utilz-vc worked the exit logic through and corrected the filing on this point; the What is left as filed and this section is the correction.

### The fix, and why it is an extraction rather than a copy

The correct shape already exists in `engine.bats`'s AT-01.2 arm: require the summary line, require the failures to be none, and require the passes to be more than none. **Copying it into `arngz.bats` would put the same parsing in two places**, which is the Highlander case (`IN-AG-HIGHLANDER-001`) that this same change moved `lua_bin` into the shared helper to avoid. Two copies of "how a Lua suite's summary is judged" can diverge: one gets a fix and the other does not.

So the parse moves once, into `opt/utilz/test/test_helper.bash`, as `assert_lua_suite_summary <label>`, and both arms call it:

- `engine.bats`, AT-01.2: `assert_lua_suite_summary engine_test`
- `arngz.bats`, AT-03.2: `assert_lua_suite_summary plan_test`, replacing `assert_output_contains "0 failed"`. `assert_success` stays.

The helper's body is `engine.bats`'s existing block with the label lifted to a parameter, so the extraction is proven by inlining it back and diffing against the old block, not by reading. Its explanatory comment moves with it and is tightened: zero arms as the live reason, the substring as the latent one, and the defence against a future driver that stops exiting nonzero on failure.

**This goes beyond decision 98 on one point, and says so here rather than in the code.** Decision 98 records `engine.bats` as changing by a comment only, relative to the bytes XYJSED was pinned to. Under this design it changes by the extraction as well: the arm's six inline lines become one call. The behaviour is the same by construction and is re-proven by the run below, but the change is not comment-only, so it is put to utilz-vc with this design, before any code exists. If it is refused, the fallback is a second inline copy in `arngz.bats`, with the Highlander debt recorded rather than hidden.

### Why it cannot weaken anything

Every input the old assertion rejects, the new one rejects. A nonzero exit fails both, through `assert_success`, which is kept. A missing summary fails both. And because exit 0 implies the summary reads `0 failed`, the old `contains` check never rejected anything `assert_success` had not already rejected. The new one additionally rejects zero arms. It is strictly stronger.

There is no prior red to preserve. AT-03.2 is ST0026's arm, ST0026 is closed and the row is green, and utilz-vc's PDY9E2 executed this arm on every arngz.bats run but never reddened it, its mutations having targeted `plan.lua` and `opt/arngz/arngz`. Strictly stronger is the whole property a fix to it needs.

### How it is proven

It sits on the stateless side of the line, so it is proven by evaluation and a green run rather than by mutation:

1. The helper's guard evaluated verbatim, with `fail` stubbed and nothing under test running, against four summaries for each label: zero arms must fail, a clean run must pass, a run with failures must fail, and a missing line must fail. This is how utilz-vc measured `engine.bats`'s guard.
2. The extraction inlined back and diffed against `engine.bats`'s current block.
3. Both arms run green in bats against the real drivers, in one booked run together with 0137.

### Not touched

ST0026's acceptance record. The arm's id, name and @test text are unchanged, so a filter selecting it by name still selects it, and utilz-vc's comment-only id annotations for ST0032 land on top without conflict.
