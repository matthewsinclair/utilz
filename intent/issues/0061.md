`.github/workflows/tests.yml` carries this line twice, at :74 in the Linux "Set up Utilz" step and again at :133 in the macOS one:

    chmod +x opt/*/[!test]* 2>/dev/null || true

`[!test]` is a CHARACTER CLASS. It means "any single character that is not `t`, `e` or `s`". It does not mean "not the word `test`". shellcheck names it SC2102.

MEASURED, by expanding the glob in this tree rather than by reading it. The pattern matches 59 of the 84 entries under `opt/*/`, and the 25 it skips are every entry whose name begins with `t`, `e` or `s`. Four of those are real utility implementations, not test directories:

- `opt/expz/expz`
- `opt/stampz/stampz`
- `opt/syncz/syncz`
- `opt/todo/todo`

So the intended exclusion of `test/` works only by the accident that `test` begins with `t`, and it takes four utilities down with it.

WHY NOTHING HAS EVER BROKEN, WHICH IS ALSO WHY THE FIX IS A DELETION. `git ls-files -s opt/` reports all four of those, and every other utility implementation in the tree, as mode `100755`. Git carries the executable bit and `actions/checkout` restores it, so the runner already has `+x` on everything under `opt/*/` that needs it, before this line runs. A loop over every utility confirms it: no `opt/<name>/<name>` is anything other than `100755`.

The line's only live effect is therefore to add `+x` to the 59 paths it DOES match, which are `README.md`, `VERSION`, `*.yaml` and directories. Nothing reads or executes those, and nothing checks the bit.

AND IT CANNOT REACH THE FILES THAT ARE ACTUALLY NON-EXECUTABLE. Fifteen files under `opt/` are mode `100644` and carry a shebang, but every one of them is nested a level deeper -- `opt/*/test/*.bats`, `opt/*/lib/*.sh`, `opt/*/lib/*.py`, `opt/utilz/tmpl/*.tmpl`. The pattern is `opt/*/[!test]*`, one level only, so it matches the `lib` and `tmpl` DIRECTORIES and never their contents. None of those files needs the bit either: `.bats` files are run by `bats`, the `lib` shell files are sourced, and the templates are copied and chmod'd by the generator.

THE FIX IS TO DELETE BOTH LINES. Every correct rewrite of the glob changes which files get `+x`, and the measurement above says the right number of files to touch is zero: the bit is already in git for everything that needs it, and the line is dead code whose only remaining function is to make documentation executable. `chmod +x bin/utilz` on the line above is in the same position and should be measured the same way before it is kept.

RECOMMENDED AFTER THE CUT, NOT BEFORE. It is latent, it is failing nothing, and today's CI run is the release gate. Changing which files get `+x` on release day buys nothing and can only move the suite. Found by devbin-vc during the 0.1.6 sweep, which correctly declined to fix it in another project's estate mid-sweep.
