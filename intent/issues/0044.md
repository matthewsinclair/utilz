title: install and upgrade announce an enclosing repository's commit for a source tree that is not a repository
status: OPEN
severity: low

`utilz install` and `utilz upgrade` announce the source tree as `source: <tree> (<state>, <commit>)` (install_announce). The commit comes from `git -C "$src" rev-parse --short HEAD` (install.sh:826 and :992), which asks no question about whether `$src` IS a repository. When it is not, git walks up to the nearest enclosing repository and answers with THAT repository's HEAD.

OBSERVED 2026-09-21, ST0019 WP-03's spike: run from a Homebrew keg, `utilz upgrade` announced `source: /opt/homebrew/Cellar/utilz/2.11.0-spike/libexec (unknown, 2f1c682db0)`. `2f1c682` is Homebrew's own HEAD: a keg has no `.git`, and `/opt/homebrew` is Homebrew's git checkout. The state beside it, `unknown`, was right, because install_tree_state asks _install_is_git_toplevel first. The two halves of one line disagreed.

WHY IT MATTERS. Nothing is written: a tree whose state is `unknown` is refused before any copy, and the keg refusal fires first anyway. But the announcement is the record of what a run looked at, and here it names a commit that has nothing to do with the tree. The same thing happens for any non-repository source that sits inside some other repository, eg an install tree under a directory that is itself a checkout.

THE FIX: one pure reader, `install_tree_commit <tree>`, answers the short HEAD only when _install_is_git_toplevel holds for the tree, which is the same test install_tree_state makes, and `none` otherwise. install and upgrade both call it, replacing their two identical lines. One bats case covers it: a tree with no `.git`, nested inside a fixture repository, announces `none`.
