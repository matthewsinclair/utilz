## What

`get_util_metadata` (`opt/utilz/lib/common.sh:87`) answers one field of a utility's yaml. It returns 1 when the yaml is missing or `yq` is absent, and otherwise prints `yq`'s answer. When `yq` cannot read the yaml, the read at `:97` fails with its stderr discarded. Every caller runs the function inside `$(...)`, where bash clears errexit, so the function goes on and ends `echo "$result"` (`:144`) with an empty result and status 0. A caller cannot tell a yaml it cannot read from a field the yaml does not carry, and each reports the first as the second:

- `--version` (`show_version`, `:186`) prints `<util> (version unknown - <util>.yaml carries no version this tree can read)` (`:225`) and exits 1. The yaml's own fault goes unnamed.
- `utilz list` (`list_utilities`, `:279`) prints `No description available` and exits 0.
- `utilz doctor`'s `[5/7]` (`run_doctor`, `:741`) reads no `utilz_version` requirement, so it reports the utilities as all properly configured. After 0080, `[6/7]` names the yaml later in the same run.
- `utilz install` and `utilz upgrade` (`install_prefix_configured`, `opt/utilz/lib/install.sh:146`) refuse with `install.prefix is not set in <tree>/opt/utilz/utilz.yaml`, which sends the reader after a key the file may well carry.

The `version_file` read (`:103`) has the same shape.

This is 0053's sibling rather than its class: an answer that cannot be read becomes an empty one, not an exit. It was seen in 0080's design and split out on vc's ruling of 19 Oct 2026, for 2.14.1, after 0080.

## Fix, for the design to settle

`get_util_metadata` returns 1 when its read of the yaml fails, and names the file and `yq`'s reason on stderr through 0080's `yaml_read_error`. Each caller's existing `|| x=""` then sees the failure, and the reason reaches the reader. Each caller words its own consequence, and `install_prefix_configured` stops saying the key is not set. The design comes after 0080 lands, since it uses 0080's helper.

1. **`get_util_metadata` answers a read it could not make with a status of its own.** Its read of the yaml (`opt/utilz/lib/common.sh:97`) and its read of `version_file` (`:103`) each become `if ! x=$(yq eval ...); then return 2; fi`. Status 2 means the yaml is there and yq could not read what was asked. It prints nothing, so each caller words its own consequence and names the reason with 0080's `yaml_read_error`. Status 1 keeps its three meanings: no yaml, no yq, or a `version_file` this tree does not carry, which already names itself on stderr (`:112`). The header gives the calling form, `x=$(get_util_metadata ...) || status=$?`, as 0080's two helpers do, and says that a bare `|| x=""` reads status 2 as absence, which is this issue's defect.
2. **Each caller names the cause.**
   - `show_version` (`:226`): status 2 from the version read prints `<util> (version unknown - <util>.yaml cannot be read: <reason>)` and returns 1, in place of "carries no version this tree can read" (`:265`). The description is not read after a version read that failed, so the reason is said once.
   - `list_utilities` (`:319`): status 2 gives the utility's row `(<name>.yaml cannot be read; utilz doctor says why)` in place of "No description available" (`:320`). The listing stays one line per utility, and doctor carries the reason.
   - `run_doctor`'s `[5/7]` (`:804`): status 2 lists the utility among those with issues, `<name> (<name>.yaml cannot be read: <reason>)`. The section then counts its issue, as it does for a utility with no implementation, and no longer says that every utility is properly configured. 0080's `[6/7]` counts its own refusal of the same file, so one unreadable yaml is two issues, one per section, each naming what its section could not check. 0080's two doctor tests that pin "one more issue" pin two.
   - `install_prefix_configured` (`opt/utilz/lib/install.sh:146`): status 2 refuses with `utilz.yaml cannot be read, so install.prefix cannot be read from it: <reason>`, naming the file, in place of "install.prefix is not set" (`:154`).
