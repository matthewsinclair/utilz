## Summary

`utilz todo` numbers its items by POSITION and renumbers every one of them on every write. The parser reads the id an item line carries and discards it (`opt/todo/todo:131-138`: "Renumbering on write means a stale id is never authoritative"), `_resolve_n` maps a number to a slot by position across DOING, then TODO, then DONE, and `--json`'s `num` is that position. `help/todo.md:26` states the model outright: "An id is a handle for the next command, not a name for the item." So a citation of item `007` goes stale at the next `add`, `done` or `sync`, and nothing reports it.

**Repro, from gtools-cc:** a `todo.md` whose items are written `003`, `007` and `009` gives `num` 1, 2 and 3 from `utilz todo --file <it> --json`, the JSON carries no field with the written number, and any write renumbers the file to `001`, `002` and `003`.

## Who needs it, and hv's word

gtools-cc's estate cites todo items by number in its boards and handovers and hand-edits its todo files to keep those numbers; every `utilz todo` write breaks the citations, and a page generated from `--json` disagrees with the file. hv ruled it in gtools-cc's session, and then in cc's, 2026-09-14: "Yeah, it should. It's bonkers that it doesn't already work like that." Via vc, the same day: in the 2.9.0 release, and the break accepted -- todo goes to 2.0.0.

## Design

- **An id is the item's name, not its position.** The written id is read and kept: each bucket carries its items' ids beside their text, every write renders each item with its own id, and `start`, `done`, `notdone` and `toggle` carry the id with the item they move.
- **A new item takes the next id never used in this file.** The frontmatter gains one key, `next-id: <n>`, the high-water mark. Parse takes the larger of it and one past the highest id present, so a hand-added item carrying a bigger id cannot collide. "Free" means never used, not currently unused: an id freed by `done --prune` or `done --flush` and handed to a new item would re-point every old citation of it at the new one, which is this defect again.
- **An item with no id**, hand-typed, gets the next id at the next write, in file order.
- **Two items with one id**, a hand-copied line: the first in file order keeps it and each later one gets the next id, with a warning naming both ids. Never silently.
- **Addressing is by id.** `start`, `done`, `notdone` and `toggle <id>` find the item whose id is `<id>`, in any bucket. A zero-padded id is read in base 10, as now, and an id no item carries is refused by name, as now.
- **Order is unchanged.** Top to bottom is still priority in DOING and TODO, and newest first in DONE. `add --top` puts an item at the top with the next id, not with id 1.
- **Width**: ids pad to three digits, or wider when the high-water mark needs it.
- **`--json`'s `num` carries the id.** Nothing else in the JSON changes.
- **The archive keeps ids**: `done --prune` writes each item as `` [x] `009` text ``, so a pruned item's citation can still be found.
- **Migration is free.** A file written by 1.x already carries ids equal to their positions, and from now on they are the items' names; a pre-2026-09 `NN:[ ] text` line keeps its `NN`.
- **Interop with `intent todo`.** The item line is unchanged byte for byte, and so is the `generator:` guard. Intent 3.x's `intent todo` projects thread status and writes no code-span ids, so there is no shared id space to reconcile, and neither tool's guard reads `next-id`.

## Version

**BREAKING: todo goes from 1.1.0 to 2.0.0.** A script that ran `todo done 1` to complete the top item now completes the item named 1, wherever it sits, or is refused if nothing carries it. hv accepted the break, via vc, 2026-09-14.

**The bump lands in 0033's own fix commit, not in the release commit.** todo's contract changes there, so `utilz todo --version` reports 2.0.0 wherever the 2.x behaviour exists. prez's 2.1.0 waits for the release commit because its design said so; this one follows the behaviour (vc's review, 2026-09-14).

## Tests, bats, red first

- gtools-cc's repro: items `003`, `007` and `009` give `num` 3, 7 and 9, and keep those ids through `sync`.
- A new item after a gap takes one past the highest id and past the high-water mark.
- `start`, `done`, `notdone` and `toggle` keep the moved item's id.
- Pruning the highest item does not free its id for the next `add`.
- An id-less line gets the next id; a duplicated id is reassigned, with a warning naming both.
- A 1.x file carrying ids and no `next-id` gains one on its first 2.x write, with every id unchanged: the migration is shown, not claimed.
- `--json`'s `num` is the item's id after `start` and `done` have moved it.

Every existing test that pins positional renumbering is rewritten to the new contract, and each one is named in the commit.

## A limit, stated rather than fixed

`next-id` is the only record of the ids above the highest one still present. Deleting that line by hand lets a pruned id be handed out again, so the docs say the key is load-bearing (vc's review, 2026-09-14).

## Docs

`help/todo.md` and `opt/todo/README.md`, wherever they promise positional renumbering (the description, the file-format notes, `sync`'s line, the examples); the usage text; and the script's header comment.
