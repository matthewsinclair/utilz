## What

hv, 10 Nov 2026, in the same message as the fixed-size window issue filed beside this one: typed into gtools-vc's window by mistake, handed to utilz-vc over the socket, received by vc's date -u of 06:02Z. hv's words and the three screenshots are quoted in that issue and in the handover, `~/Devel/scratch/utilz-vc/arngz-handover-20261110.md` (sha256 c0727ec6708e3f1dee92968a470a441b89e6c4570de555a7c46c4da9d99426b8, 130 lines, banked by vc from gtools-vc's scratch and byte-identical to it). utilz-vc re-derived the analysis from the log and the source first-hand before filing.

utilz 2.14.8 from Homebrew with arngz 1.1.2, on rhadamanth (macOS, the Hammerspoon engine). main at 69171b43 carries arngz 1.1.3; this defect is in both.

`arngz discover` snaps each window it records to the desk's grid. A window whose frame begins off its display, as happens on a multi-monitor desk where a window sits on a monitor left of the origin, is **clamped into the edge cell** rather than left out or refused. `discover` says so in its report, exits 0, and saves the entry anyway. The next `apply` of that desk then fails the entry, because the clamped frame is not a size the app will take.

hv's run 69 (`Discover…` of zeophq, 2026-11-10T05:19:19Z, exit 0) reported:

```text
main desktop 1: notion.id "Meetings" spans part of a cell; snapped to 0,0 1x4, 1920px off
```

and run 70, an apply of the desk run 69 had just saved, on the same screens 20 s later, failed that entry:

```text
the window took 0,40 640x1089, not 0,40 225x1089
```

225 px is below Notion's minimum width, so the app refused it. The 1x4 cell the clamp produced is narrower than the window can be.

Repro: on a desk whose display has a monitor to its left, place a window on that left monitor, run `arngz discover --save <desk> --force`, then `arngz apply <desk>`. discover exits 0 and records the window in the edge cell; apply reports it failed and exits 1.

## Measured

Read first-hand by utilz-vc at main's head 69171b43, and from hv's `~/.local/state/menuz/menuz.log`.

- `opt/arngz/lib/plan.lua:1093`, `snap_axis`, the pure function that snaps one axis of a window to the grid:

  ```lua
  local a0 = clamp(round(a), 0, cells - 1)
  local b0 = clamp(round(b), a0 + 1, cells)
  ```

  where `a` is the window's start in cells from the display's origin. A frame starting left of that origin gives a negative `a`, which clamps to cell 0, and `b0` is then forced to at least one cell past `a0`. So a window 1920 px off the display is recorded as occupying the edge cell, and run 69's `0,0 1x4` with `1920px off` is exactly that arithmetic.
- The report already measures the distance and already says `spans part of a cell`, so `discover` holds the number it needs to refuse the entry. It lacks only the rule that says to.
- Run 70's Notion failure is this defect's downstream consequence, and it is one of the two failures that made run 70 exit 1 (the other being the fixed-size window issue filed beside this one).
- notion.id also failed in runs 39, 40 and 44 for a **different** cause, that its title bar is an `AXWebArea` arngz cannot take hold of to carry the window between desktops. That is not this issue and is not filed.
- The 1920 px offset is consistent with homere's left monitor (an HG560T34), but the observed frame was not kept by the run, so the exact origin is an inference from `snap_axis`'s arithmetic rather than a reading. The clamp itself is read from the source and is not in doubt.

Why it matters: `discover` is the one verb whose whole job is to record a desk that will apply. A desk it has just saved, applied straight afterwards on the same screens, is the test that tells a real defect from the environment, and this defect makes that test fail by writing an entry that cannot be placed. It also writes that entry into hv's Molt-matts working tree, where the desks live as `config/arngz/desks/`, so a bad record persists into a committed desk unless someone notices the report line.

## Fix

utilz-vc's recommendation: `discover` leaves out a window lying mostly off its display, and names it in its report with the distance it measured, so a desk records only what it can place. "Mostly" needs a threshold, and the recommendation is the window's **centre** falling outside the display: it is unambiguous, needs no measurement discover does not already make, and cannot be argued about at a boundary the way a percentage can.

Alternative, hv's to pick instead: record the window against the display it is actually on. A larger change, and right only where that display is itself part of the desk, so it does not help the common case of a window parked on a monitor the desk does not describe.

Not in this fix:

- Notion's `AXWebArea` title bar (runs 39, 40, 44), which stops arngz carrying the window between desktops.
- The fixed-size window case, filed as its own issue beside this one. Run 70 needs both fixed before it is clean.

## Design

utilz-vc, 10 Nov 2026, ST0032/02, each file:line read at main's head 35025ba0. Size: S.

This one is wholly in the pure layer, so it is wholly provable: `P.desk_from_world` (`plan.lua:1239`), which is what `discover` prints, is marked PURE in its own comment and is already exercised by `plan_test.lua` under plain Lua. No engine line changes.

**The defect's exact site.** In `desk_from_world`'s per-window branch (`plan.lua:1283` to `:1297`), a window that is not fullscreen is snapped unconditionally:

```lua
local layout, misfit, partial = P.snap(w.frame, s.frame, grid)
app.layout = layout
if misfit > 0 then app.misfit = string.format("%dpx", misfit) end
if partial then note("... spans part of a cell; snapped to %s, %dpx off", ...) end
```

`P.snap` delegates to `snap_axis` (`plan.lua:1093`), whose `clamp(round(a), 0, cells - 1)` and `clamp(round(b), a0 + 1, cells)` turn a negative start into cell 0 with a width of at least one cell. So the entry is recorded in the edge cell and the note says only that it "spans part of a cell", which reads as a rounding nicety rather than as a window that is not on this display at all. Run 69's `snapped to 0,0 1x4, 1920px off` is that: `off_a` is `|start - (origin + 0)|`, so the frame began 1920 points left of the display's origin, which also settles the inference the `## Measured` section left open.

**The fix follows an idiom already in this function.** Where a window cannot be recorded, `desk_from_world` notes why and sets `app = nil` so it is never appended (`plan.lua:1271` to `:1276`, the window whose title does not tell it from its app's others). This change adds a second such case rather than inventing a mechanism.

1. **A pure predicate, one home for the geometry.** Beside `P.snap` (`plan.lua:1107`), add `P.mostly_off(frame, screen_frame)`: true when the window's centre, `frame.x + frame.w / 2` and `frame.y + frame.h / 2`, lies outside `screen_frame`. The centre is the threshold hv's ruling asked for, chosen because it needs no measurement the function does not already have and has no arguable boundary: a window is on the display its middle is on. It lives beside `P.snap` because it is the same geometry over the same two rectangles, and `snap_axis` is left exactly as it is, since its clamping is correct for a window that genuinely is on the display.

2. **`desk_from_world` refuses the entry.** In the non-fullscreen branch, before the snap:

   ```lua
   if P.mostly_off(w.frame, s.frame) then
     note("%s desktop %d: a window of %s is not recorded: it lies mostly outside this display's"
       .. " usable area (its centre is %d,%d and that area is %d,%d %dx%d)", label, si, w.bundle,
       round(w.frame.x + w.frame.w / 2), round(w.frame.y + w.frame.h / 2),
       round(s.frame.x), round(s.frame.y), round(s.frame.w), round(s.frame.h))
     app = nil
   else
     ... today's snap, unchanged ...
   end
   ```

   The wording matches the existing refusal's shape, "a window of %s is not recorded: ...", so a reader of the report meets one phrasing for one meaning. Fullscreen windows are untouched: they take the `fullscreen` layout and are never snapped.

3. **What this deliberately does not do.** It does not try to record the window against the display it is really on. That is a bigger change and is right only where that display is itself part of the desk, so it does not help the common case this issue is about, a window parked on a monitor the desk does not describe. It is named in `## Fix` as the alternative hv did not pick.

4. **Tests, red at the base and green at the fix**, all pure, under plain Lua:
   - `plan_test.lua`: `P.mostly_off` is true for a frame whose centre is left of the display, right of it, above it and below it; false for a frame wholly inside; false for a frame hanging over an edge with its centre still inside, which is the case that must keep working as it does today;
   - `plan_test.lua`: `desk_from_world` given a world with a window at `x = -1920` on an `8x4` grid over a display at `0,0` records **no** app entry for it and emits a note matching `is not recorded: it lies mostly outside this display's usable area`. The frame uses run 69's own numbers rather than invented ones;
   - `plan_test.lua`: the same world with that window moved wholly onto the display records it and notes nothing, which is the guard against the predicate excluding too much;
   - `plan_test.lua`: the existing partial-cell check at `:1043` keeps its answer, since VSCode's 75px misfit is a window on its display and must still be recorded with its note. That is the regression guard on this change, and it is an existing test, not a new one;
   - `arngz.bats`: the existing discover assertion at `:686` is unchanged and is the shim-level guard.

   No expected count is written by hand: each check asserts its own outcome. (That held for these arms, but it is an assertion of compliance with the project's no-magic-numbers rule rather than something the arms demonstrate, and the same sentence stands in ST0032's design, under which WP04's arms were written with three hand-written counts that had to be derived out afterwards.
