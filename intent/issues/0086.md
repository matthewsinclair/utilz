utilz-ic found it on 19 Oct 2026 in gtools-vc's slot 112, while 0073's icon fix-forward ran `utilz menuz test`: RunnerTests.idsUnderContention() failed with four issues, none in the code under change, after passing in slots 79, 85, 95, 100, 102 and 105.

## What

menuz takes each run's id from `<state>/next-run` under an exclusive lock (`Runner.takeId`, `Menuz/Services/Runner.swift:27` to `:55`). Its design says only a store that does not exist yet starts at 1, and one that exists and holds no id is refused, never read as 1, since a write never shortens it (`MenuzKit/Sources/MenuzKit/RunId.swift`). A store that has just been created is the exception: it exists and holds nothing until its creator writes it.

A taker that finds no store creates it with `open(path, O_RDWR | O_CREAT | O_EXCL | O_EXLOCK)`. On macOS the file is created, and visible by its path, before that open takes its lock, so a second taker's `open(path, O_RDWR | O_EXLOCK)` can find the new, empty file and take the lock first. It reads nothing, with `created` false, and `RunId.parse("")` refuses it as `Unreadable(text: "")`. That taker's run gets no id, and the app logs `"<label>" not run: <state>/next-run holds no id: ` with nothing after the colon (`Menuz/MenuzApp.swift:318`).

## Measured

Slot 112 (19 Oct 2026, 09:26:28Z to 09:26:56Z), wt-0073 at `2d1ea40`: two takers of 100 ids each, at once, on a fresh store. `taken.failures` was `[""]`, 199 ids came back, not 200, and their set missed one (`MenuzTests/RunnerTests.swift:96` to `:100`). It is rare: it needs two takers in the window between the store's creation and its creator's lock, so in use, two runs started at once on a machine whose store does not exist yet, which is a first launch; the test makes that window every run, and loses it only under load.

## Fix

Never let the store be seen empty. A taker that finds no store writes `1\n` to a temporary file beside it and `link()`s that to `next-run`, which fails with `EEXIST` when a store is already there, then removes the temporary file either way; every taker then opens the store and takes its lock as a store that exists, so the creator takes id 1 through the ordinary read under the lock, and `RunId.parse(nil)`'s "does not exist yet" case goes. A failure says what failed, never an empty text: an empty store under the lock is refused as `next-run is empty`, which after the fix only a store emptied by something else can be.

## Design

utilz-ic, 19 Oct 2026, for vc's read, with `Runner.takeId` read at `2d1ea40`.

1. **The store is never seen empty.** A taker that finds no store writes `1\n` to a temporary file in the state directory, `link()`s it to `next-run`, which is atomic and fails with `EEXIST` when a store is already there, and removes the temporary file either way. Every taker, the creator included, then opens `next-run` with `O_EXLOCK` and reads, takes and writes under the lock, so the creator takes 1 by the ordinary path, and `created` and `RunId.parse(nil)`'s "does not exist yet" case go.
2. **A refusal says why.** An empty store under the lock, which no menuz then makes, is refused as `next-run is empty`, so the app's line never ends in a colon.
3. **The tests.** The window is inside one `open()`, which no test can pause, and the fix removes the window rather than narrowing it, so no single test can go red on main and green on the fix through the same seam. Two, then:
   - **The symptom, on demand, red on main.** The test makes `next-run` as a creator shows it inside the window, created and empty, with no lock, and runs a taker against it. On main the taker is refused with an empty text. With the fix it is refused as `next-run is empty`, which pins point 2, the only part of the fix that state can still reach.
   - **The cause, pinned on the fix.** `takeId` gains a seam, `takeId(stateDir:beforeLink:)`, whose `beforeLink` defaults to nothing. The test holds the creator at that point, with its temporary file written and not yet linked, and checks that no `next-run` exists yet, and that a second taker run then takes 1 while the held creator, released, takes 2. On main this test cannot compile, since main has no such point to hold.
   - `idsUnderContention` stays as the load check.
4. **Runs,** each booked: the red, then the green, `utilz menuz test` in a worktree on main's head; vc's read of the bytes; the landing by path. menuz's version is hv's and vc's to set.

## Design amendment: critic-swift's first review

utilz-ic, 19 Oct 2026, for vc's read. critic-swift reviewed runs/0086-full.patch (sha256 2b74230c) and found one CRITICAL and two RECOMMENDATIONs, banked as `~/Devel/scratch/utilz-ic/runs/0086-critic-1.md`. All three are taken. They change design points 2 and 3.

5. **The cause test looks where a second taker would** (the CRITICAL, IN-AG-RED-CONTROL-001).
   - storeMadeWhole read nothing inside its hold. So two breaks that bring the empty window back passed every assertion: a maker that links its temporary file before writing it, and main's create with the hold placed just before it.
   - Inside the hold, before the second taker runs, the test now lists the state folder and reads each file in it. The folder must hold the maker's temporary file alone, with no `next-run`. That file must already hold `RunId.stored(after: 0)`.
   - The first break leaves the file empty, and the second leaves no file, so each goes red with the seam unchanged.
   - The green's slot shows the first break red before it runs the green: makeStore's link is moved ahead of its write and the suite runs, then the file is restored and its diff hash checked.
6. **errno is saved before any string is built** (IN-AG-NO-SILENT-001).
   - It is saved after mkstemp and after link, as it already is after write. The EEXIST test and both messages use the saved values.
   - The temporary file is made with `mkostemp(&template, O_CLOEXEC)`, so it is close-on-exec like takeId's other descriptors.
7. **A refusal's kind is in its type, not its text** (IN-SW-CODE-002).
   - Main's `Unreadable(text:)` held three things in one field: a store's own text, the empty refusal's wording, and every I/O failure's reason. The app logged each of them as `holds no id: <text>`.
   - `RunId.Unreadable` becomes an enum: `empty`, `holds(String)` and `failed(String)`, and each failure names its step.
   - Its description is what the app's line says after the store's path: `"<label>" not run: <state>/next-run <description>`. The descriptions are:
     - `is empty`, design point 2's wording;
     - `holds no id: <text>`, as today;
     - for a failure, the step and why: `is in a folder that could not be made: …`, `could not be opened: …`, `could not be read: …`, `could not be written: …`, `could not be cut to its length: …`, `could not be made, as its temporary file could not be created: …`, `could not be made, as its temporary file could not be written: …` or `could not be linked into place: …`.
   - A store whose text is `is empty` is now `holds("is empty")`, never the empty refusal.
   - critic-swift also offered a smaller fix: quote the store's text and document the I/O reasons. It would leave the app logging an I/O failure as a store holding no id, so it is not taken.
   - Point 3's red changes with the type. The empty store's expectation now reads the refusal's description. So the same line compiles on main, where it fails showing `Unreadable(text: "")`, and on the fix, where it reads `is empty`.

   - A state folder on a volume without hard links refuses every run, and the refusal names the cause. That is the settled cost of having no fallback.
