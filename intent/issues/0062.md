`tools/ci-state` is the `ci.query` the release core runs at step 11, and step 11 has never run on this project or on devbin. It is about to run for the first time during a cut, which is the worst moment for an answer that cannot be acted on.

WHAT IT READS. `tools/ci-state` asks `install_ci_state` (`opt/utilz/lib/install.sh`), which runs:

    gh run list ... --json status,conclusion,databaseId --limit 20

That is the RUN's conclusion. It never reads the run's JOBS. Every conclusion other than `success` is ranked as a verdict and translated to `failed <conclusion>: <run id>`, which refuses the cut at step 11.

THE GAP. A run can conclude `failure` without a single test having failed -- a billing refusal, an unavailable runner, a cancelled or expired job -- and at the run level that is INDISTINGUISHABLE from a suite going red. devbin-vc measured four such runs in devbin's own history, three of them with every test job green and only the summary job refused. The detail this project would print in that case is `failed  failure: <run id>` and nothing else, so the reader cannot tell "the code is broken" from "CI never ran the code", which are opposite actions.

This is a DIAGNOSABILITY defect, not a correctness one. Refusing the cut is right in both cases: an infrastructure refusal means there is no verdict, and a release should not proceed on no verdict. The defect is that the refusal does not say which of the two it is, at the exact moment a human is mid-cut and deciding whether to fix code or re-run CI.

THE FIX. When the chosen run's conclusion is not `success`, read that run's jobs as well -- `gh run view <id> --json jobs` -- and name in the detail either the jobs that failed, or the fact that no job ran. The run-level read stays as it is; this adds a second call only on the not-success path, so the green path costs nothing. Note the related trap already recorded in issue 0052: a release sha carries two runs, the branch's and the tag's, and the verdict is the worst of them, so the job read must be of the run that produced the verdict rather than of the newest.

AND A CAVEAT FOR THE READER TODAY, whatever is done about the code: when step 11 refuses during hv's cut, read the JOBS on GitHub before touching anything. The run conclusion alone does not say what happened.

RECOMMENDED AFTER THE TAG. Nothing is broken today; CI is green on the tree to be cut. This is filed now because step 11's first live run is today and the finding would otherwise be lost. Raised by devbin-vc from devbin's own measured history.
