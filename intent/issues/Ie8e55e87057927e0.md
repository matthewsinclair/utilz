# menuz hard-codes the release asset's name, which the core derives

Found in ST0031/01's re-plan on 23 Nov 2026, and filed on vc's word.

## The defect

menuz's fetch_asset, the keg's install of the app, names the release asset twice by literal:

- opt/menuz/menuz:915 builds the download URL with `Menuz.app.zip`;
- opt/menuz/menuz:917 names the zip it saves the same way.

The release core derives the same name from bin/.devbin/config.yaml in cfg_macos_app_asset (bin/.devbin/lib/config:1012-1026). The name is macos.asset, or the app's own name with .zip where that is not declared. The core attaches the zip under that name at a cut.

While the two agree, nothing fails. A rename on either side would leave `menuz install` fetching an asset no release carries, and the cut would still pass. This is IN-AG-HIGHLANDER-001. It is vc decision 91's sixth finding, whose copy in tools/post-cut retires with ST0031/01, leaving these two.

## The fix (XS)

It follows issue 0106's pattern for the bundle id:

- one home for the name, `MENUZ_ASSET`, in opt/menuz/lib/launch-services.sh, which menuz sources (menuz:32-34);
- fetch_asset uses it at both lines;
- an arm in opt/menuz/test/macos.bats holds it equal to the core's cfg_macos_app_asset, as the arm at :265-274 holds macos.bundle_id equal to MENUZ_BUNDLE_ID.

## When

It is XS, so it rides ST0031/01's code (vc, 23 Nov 2026).
