## What

`utilz use dev` and `utilz relink` repoint the PATH links that already exist and make none. `install_verb_relink` (`opt/utilz/lib/install.sh:1288`) relinks only what `install_link_census` (`:1252`) lists, and the census walks the symlinks already in the bin dir. So a utility added since the links were made never gets one, and the report ("N changed, M already correct, K left alone") does not name it.

On hv's machine, `~/.local/bin` holds links made on 22 Sep 2026 for the fifteen utilities of that day, plus `utilz`, and none for arngz or menuz (both 16 Oct). On 19 Oct, after a `brew unlink utilz`, both left hv's PATH, and `use dev` could not bring them back. The keg was relinked to restore them.

## Measured

19 Oct 2026, at `4611b1c`: `ls -la ~/.local/bin` shows `cleanz` to `xtrct` and `utilz` pointing into the source tree, and no `arngz` or `menuz`. No other verb makes a PATH link: the `ln -s` at `install.sh:553` copies a tree's own links when it publishes.

## Fix

1. `relink`, and so `use`, links every utility of the tree that has no link in the bin dir, and reports each one as `linked:`.
2. A test pins it: a bin dir missing one utility's link gets the link, and the report names it.
3. `help/utilz.md`'s `use` and `relink` sections say so, and the CHANGELOG under `[2.14.1] - unreleased`.

Owner cc, routed by vc on hv's word that everything outstanding ships in 2.14.1 (19 Oct 2026).

## Design

cc, 19 Oct 2026, with each file:line re-read at main's head `23d7575`, where `opt/utilz` is as it was at `4611b1c`. Size: S.

Read on hv's machine today: the install at `~/Devel/opt/utilz` is utilz 2.10.0 (`3ee6992`) with fifteen utilities, neither arngz nor menuz, and the sixteen links in `~/.local/bin` point into the source. So the fix has to hold both ways: `use dev` links arngz and menuz into the source, and a later `use opt` must not then point them at an install that lacks them, which relink would do today (item 3). This departs from the Fix above in two places, items 2 and 3.

1. **The one walker of `bin/` walks the tree it is given.** `each_utility` (`opt/utilz/lib/common.sh:548`) takes an optional tree, `$UTILZ_HOME` when none is given, and walks `"$tree"/bin/*` (`:551`). Its seven callers pass nothing, so nothing they do changes. relink needs the target tree's utilities, not the running tree's: `use opt` from the checkout must not link a utility the install lacks, and relink's suite runs with `UTILZ_HOME` at the real checkout (`opt/utilz/test/test_helper.bash:20`), where a walk of the running tree would link the seventeen real utilities into a fixture bin dir.
2. **relink links what the target tree has and the bin dir lacks.** After the census loop (`opt/utilz/lib/install.sh:1357` to `:1395`), relink walks `each_utility "$prefix"`, but only when the census found at least one link into a Utilz tree. A bin dir holding no Utilz link gets none, as today, so relink pointed at the wrong directory adds nothing to it. That is the first departure: the Fix links every utility the bin dir lacks, wherever it is. For each name with nothing at `$bindir/<name>`, relink makes `$bindir/<name> -> $prefix/bin/<name>` and prints `  linked:    <name> -> <target>`. A name held by a file that is not a link is left alone and reported as `  skipped:   <name> (not a link)`. A name held by a link is the census's to handle. The summary (`:1397`) becomes `<n> changed, <n> linked, <n> already correct, <n> left alone`.
3. **relink no longer points a link at a utility the target tree lacks.** It repoints without looking today (`:1387` to `:1389`), so on hv's machine, once item 2 has linked arngz and menuz into the source, `use opt` would make both dangling links and report them relinked. A link whose name has no `bin/<name>` in the target tree is now left pointing where it does, and reported as `  skipped:   <name> (not in <prefix>)`. This is read from the code and not yet run. It is the second departure: a second defect in the same verb, which item 2 makes reachable. It goes in 0079 unless vc wants it as its own issue.
4. **What does not change.** `install_link_census` (`:1252`) stays the one walk of the bin dir: the new step walks the tree with `each_utility` and looks in the bin dir by name, never listing it. `use` (`:1518`) stays a coordinator over relink and gains all of this through it, and the bare `use` report (`:1448`) is unchanged. install and upgrade still never touch a PATH link.
5. **The tests, red first,** in `opt/utilz/test/relink.bats`, over `make_fake_src`, whose one utility is `alpha` (`test_helper.bash:508`):
   - a bin dir with Utilz links and none for `alpha` gets `alpha -> <install>/bin/alpha`, the report names it `linked:`, nothing else appears in the bin dir, and a second run reports `unchanged: alpha`;
   - a link for `gamma`, a utility the source gained after the install was published, still points into the source after `relink --prefix <install>`, and the report names it;
   - a bin dir holding no Utilz link gets no `alpha`, and a plain file named `alpha` among Utilz links is left byte for byte, and reported.

   On main the first two fail. The third's first half passes on main by design, pinning that the new step stays out of a directory that is not Utilz's, and its second half fails for want of the report.
