## What

utilz-ic, 23 Oct 2026, in the Launch Services readbacks of its todos 8 and 9 after 2.14.2's publish. vc confirmed it the same day and gave it to utilz-ic as an issue of its own, separate from 0103 though in the same file, to ride the next release beside it.

`bin/devbin macos publish` proves its zip the way a download meets it. It unpacks the zip into a temporary `unpacked/` directory, checks the `Menuz.app` there, and removes the directory. Launch Services keeps a record of each unpacked `Menuz.app` under menuz's bundle id after the directory is gone. So every run leaves one more record of the bundle id, pointing at a path that no longer exists. Those records are what `open -a`, the login item and a later install resolve among. menuz's own install already unregisters the build product it installs from, for that reason (`opt/menuz/menuz:886`: "So Launch Services never opens the build product for the bundle id").

## Measured

23 Oct 2026, with `lsregister -dump` read for records under `com.matthewsinclair.utilz.menuz`.

- `cmd_publish` (`bin/.devbin/cmd/macos:483` to `:515`):
  - It makes `staging` with `mktemp -d` (`:497`) and zips the stapled bundle into it.
  - It unpacks the zip into `$staging/unpacked` with `ditto -x -k`, then runs `app_ship_blockers` and `app_verify_notarised` on `$staging/unpacked/Menuz.app`.
  - It uploads, and removes `$staging` with `rm -rf` on every path out (`:500`, `:504`, `:508`, `:510`, `:512`, `:513`).
  - Nothing unregisters the unpacked bundle, and `cmd/macos` calls `lsregister` nowhere.
- After 2.14.2's two publish runs, three records of the bundle id named `/private/var/folders/.../T/tmp.<X>/unpacked/Menuz.app` with the path gone from disk:
  - `tmp.GYPqg7Uhtf` (record `0x4ed9c`), already there before 2.14.2 (utilz-dc's read on 22 Oct).
  - `tmp.MVuQSYPjhj` (`0x5894c`) and `tmp.qKzTSmncRq` (`0x58944`), one for each of 23 Oct's two runs.
  - ic's todo 9 dropped all three with `lsregister -u`, which drops a record whose path is gone.
- Two kinds of temporary copy left no record:
  - `app_verify_notarised`'s quarantined copy (`$t/Menuz.app`, made with `ditto` and assessed by `spctl` alone, `cmd/macos:311` to `:327`). One was made in each of the day's `app-notarize` and `publish` runs.
  - The Homebrew `menuz install`'s unzipped copy (`fetch_asset`: `ditto -x -k`, then `codesign --verify` and `spctl`), in ic's slot 255.
- The one step only the unpacked copy gets is `xcrun stapler validate` on it directly (`cmd/macos:305`), so that is the likely registrar. This is unproven.

## Fix

1. `publish` unregisters its unpacked proof copy before it removes `$staging`.
   - It does so on every path out, the refusals included, through one helper that unregisters what was unpacked and then removes the staging directory, so no exit path forgets it.
   - A failed unregistration is said, not dropped.
   - `lsregister` is found as menuz finds it: one on PATH first, which is a test's fake, then the system's path (`opt/menuz/menuz:169` to `:173`).
2. Tests in `opt/menuz/test/macos.bats`, sharing 0103's fixture:
   - A fake `lsregister` on PATH records its calls.
   - `publish`'s pass case, and each refusal after the unpack, shows `-u <staging>/unpacked/Menuz.app` before the staging directory is gone.
3. The registrar is measured before any code, as the design's first proof. This is a light run booked with vc:
   - unzip the release zip into scratch;
   - read `lsregister -dump` before and after `stapler validate` on it;
   - unregister and remove the copy.
   If `stapler validate` is not the registrar, the design says which step is.
4. Not here: `app-notarize`'s quarantined copy, which left no record (Measured).
