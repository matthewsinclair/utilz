## What

utilz-ic, 23 Oct 2026, in the Launch Services readbacks of its todos 8 and 9 after 2.14.2's publish. vc confirmed it the same day and gave it to utilz-ic as an issue of its own, separate from 0103 though in the same file, to ride the next release beside it.

`bin/devbin macos publish` proves its zip the way a download meets it. It unpacks the zip into a temporary `unpacked/` directory, checks the `Menuz.app` there, and removes the directory. Launch Services keeps a record of each unpacked `Menuz.app` under menuz's bundle id after the directory is gone. So every run leaves one more record of the bundle id, pointing at a path that no longer exists. Those records are what `open -a`, the login item and a later install resolve among. menuz's own install already unregisters the build product it installs from, for that reason (`opt/menuz/menuz:886`: "So Launch Services never opens the build product for the bundle id").

## Measured

23 Oct 2026, with `lsregister -dump` read for records under `com.matthewsinclair.utilz.menuz`.

- `cmd_publish` (`bin/.devbin/cmd/macos:483` to `:515`):
  - It makes `staging` with `mktemp -d` (`:497`) and zips the stapled bundle into it.
  - It unpacks the zip into `$staging/unpacked` with `ditto -x -k`, then runs `app_ship_blockers` and `app_verify_notarised` on `$staging/unpacked/Menuz.app`.
  - It uploads, and removes `$staging` with `rm -rf` on every path out (`:500`, `:504`, `:508`, `:510`, `:512`, `:513`).
  - Nothing unregisters the unpacked bundle, and `cmd/macos` calls `lsregister` nowhere.
- After 2.14.2's two publish runs, three records of the bundle id named `/private/var/folders/.../T/tmp.<X>/unpacked/Menuz.app` with the path gone from disk:
  - `tmp.GYPqg7Uhtf` (record `0x4ed9c`), already there before 2.14.2 (utilz-dc's read on 22 Oct).
  - `tmp.MVuQSYPjhj` (`0x5894c`) and `tmp.qKzTSmncRq` (`0x58944`), one for each of 23 Oct's two runs.
  - ic's todo 9 dropped all three with `lsregister -u`, which drops a record whose path is gone.
- Two kinds of temporary copy left no record:
  - `app_verify_notarised`'s quarantined copy (`$t/Menuz.app`, made with `ditto` and assessed by `spctl` alone, `cmd/macos:311` to `:327`). One was made in each of the day's `app-notarize` and `publish` runs.
  - The Homebrew `menuz install`'s unzipped copy (`fetch_asset`: `ditto -x -k`, then `codesign --verify` and `spctl`), in ic's slot 255.
- The one step only the unpacked copy gets is `xcrun stapler validate` on it directly (`cmd/macos:305`), so that is the likely registrar. This is unproven.

## Fix

1. `publish` unregisters its unpacked proof copy before it removes `$staging`.
   - It does so on every path out, the refusals included, through one helper that unregisters what was unpacked and then removes the staging directory, so no exit path forgets it.
   - A failed unregistration is said, not dropped.
   - `lsregister` is found as menuz finds it: one on PATH first, which is a test's fake, then the system's path (`opt/menuz/menuz:169` to `:173`).
2. Tests in `opt/menuz/test/macos.bats`, sharing 0103's fixture:
   - A fake `lsregister` on PATH records its calls.
   - `publish`'s pass case, and each refusal after the unpack, shows `-u <staging>/unpacked/Menuz.app` before the staging directory is gone.
3. The registrar is measured before any code, as the design's first proof. This is a light run booked with vc:
   - unzip the release zip into scratch;
   - read `lsregister -dump` before and after `stapler validate` on it;
   - unregister and remove the copy.
   If `stapler validate` is not the registrar, the design says which step is.
4. Not here: `app-notarize`'s quarantined copy, which left no record (Measured).

## Design

utilz-ic, 23 Oct 2026, for vc's read before any code, with vc's four notes on slot 259's END taken in. Size XS. It lands after 0103, in the same worktree off main, as its own commit with its own bytes, slot and landing (vc's word). The line numbers are main's at ff38a4a2, before 0103's bytes move them.

1. **The registrar, measured.** This was slot 259, light, booked with vc: ic's `m0104-registrar.sh` on the release zip, with each Launch Services read taken 5 s after its step.
   - After `ditto -x -k` into a `mktemp -d` staging dir's `unpacked/`, as `publish` does it: no new record. After the plutil reads that `app_ship_blockers` makes: none.
   - After `xcrun stapler validate` on the unpacked bundle: its record appeared, in that step's own read, before the quarantined copy existed.
   - After `app_verify_notarised`'s quarantined copy and `spctl`: no record for that copy.
   - `lsregister -u` dropped the unpacked copy's record. On the quarantined copy, which had none, it exited non-zero: `failed to scan <path>: -10814 from spotlight`.
   - The final read equalled the first.
   - Launch Services lists the copy by its resolved path, `/private/var/folders/...`, where `mktemp -d` gave `/var/folders/...`.

   So `publish`'s `stapler validate` (`bin/.devbin/cmd/macos:305`, through `app_verify_notarised`) is what registers the proof copy.
2. **Keep the check, and drop its record** (vc's note 2). A check that registered nothing could replace `stapler validate` only if it proved the same thing: a ticket stapled into the bundle inside the zip. No such check has been measured. Reading the zip's listing for the ticket would prove its presence, not its validity, and `syspolicy_check` is unmeasured here. So `stapler validate` stays, and its record is dropped after it.
3. **One helper for every path out, judged by the postcondition** (vc's note 1). `cmd_publish` removes `$staging` in six places (`:500` to `:513`), and each becomes a call through one helper, `app_drop_proof_copy <staging>`. It:
   - takes the unpacked bundle's path as Launch Services lists it: the staging dir resolved with `pwd -P`, plus `/unpacked/Menuz.app`;
   - runs `lsregister -u` on it, keeping lsregister's answer for the message and parsing nothing in it;
   - removes `$staging`;
   - reads `lsregister -dump` whole into a variable before searching it (it runs to tens of megabytes), and requires that no record's path, read without its ` (0x...)` id, equals the bundle's.

   When the record is still listed, or the dump cannot be read, the helper prints one clause on its stdout and returns 1: `could not drop the Launch Services record for <path>: <why>; drop it with: <lsregister> -u <path>`, where `<why>` carries lsregister's answer, or the dump's failure. It prints nothing to stderr itself, so each path out says the clause exactly once. This covers `-10814`, a path never unpacked and every other answer alike: only the dump decides.
4. **What publish says** (vc's note 3).
   - The five refusals (`:500`, `:504`, `:508`, `:510`, `:512`) go through `publish_refuse <staging> <message>`. It runs the helper, warns its clause if there is one, then dies with the refusal's own message, unchanged from today.
   - After an upload that worked, a clause makes `publish` exit 1 with a message that leads with what is true: `published Menuz.app.zip on release <tag>; could not drop the Launch Services record for <path>: <why>; drop it with: <lsregister> -u <path>`. It never suggests a rerun, which would refuse on the existing asset.
5. **Finding lsregister.**
   - As menuz finds it (`opt/menuz/menuz:169` to `:173`): one on PATH first, which is a test's fake, then the system's path.
   - The system's path is the one menuz names at `opt/menuz/menuz:160`. `cmd/macos` is a devbin command and does not source menuz, so it carries the path as a constant beside its others (`:43` to `:48`), with a comment naming menuz's. It already does the same with the bundle id (`APP_BUNDLE_ID` at `:44`, menuz's `BUNDLE_ID` at `opt/menuz/menuz:158`).
   - Whether that pair stands, or both move to one place, is vc's call.
6. **Tests** in `opt/menuz/test/macos.bats`, on 0103's fixture, with a test for each path out (vc's note 4). The fakes model what slot 259 measured:
   - A fake `lsregister` keeps its records in a file. `-u <path>` drops the path's record, or exits 1 with `failed to scan <path>: -10814 from spotlight` when it holds none. `-dump` prints each record in the dump's shape (a `path:` line with its id, an `identifier:` line and the separator). `$FAKES/ls.stuck` makes `-u` exit 0 and keep the record.

   - The fake `gh` fails `release upload` when `$FAKES/upload.fail` exists.
   - The fake `ditto -x` rewrites the unpacked copy's `MenuzKind` when `$FAKES/unpack.kind` exists, so the unpacked copy alone fails a blocker (0103's kind reason).
   - The tests, each reading the record list through the fake's `-dump`:

     - **The upload failed:** exit 1 with the refusal, and no record.
     - **A blocker refused:** exit 1 with the refusal, no record, and the helper's `-u` call made, so this path too goes through the one helper.
     - **The record stuck:** exit 1, the message leading with `published Menuz.app.zip on release <tag>`, naming the path and the command, and said once.
