## Summary

`opt/prez/prez`'s staleness check (`prez_is_stale`, `:155-174`) and cargo answer "is the binary stale?" by different rules, and **the rebuild the shim triggers cannot clear the condition the shim detects.** From the source tree, every `utilz prez <verb>` prints `prez: sources changed, rebuilding...`, runs a `cargo build --release --workspace` that relinks nothing (`Finished ... in 0.03s`), prints `prez: built`, and does it all again on the next run. hv asked on 2026-09-14: "What is this line? ... and why does it print every time?"

- **The shim** asks whether any path under `crate/`, except `target/`, is newer than the OLDER of the two built binaries.
- **Cargo** asks whether any file a binary is actually built from has changed, and relinks only that binary.

## Measured 2026-09-14 by vc (source tree, `CARGO_TARGET_DIR` unset)

| What                                                     | Measured               |
| -------------------------------------------------------- | ---------------------- |
| `target/release/prez` last linked                        | 2026-09-10 08:05 local |
| `target/release/showreel` last linked                    | 2026-09-11 09:57 local |
| paths the shim's walk finds newer than `prez`            | 20                     |
| `prez`'s own inputs (per `prez.d`) newer than it         | 0 of 25                |
| `showreel`'s own inputs (per `showreel.d`) newer than it | 0 of 22                |

The 20 are showreel's sources and `fixtures/45h.showreel.yaml`, the three `Cargo.toml` files, `Cargo.lock` and `tests/manifest.rs`, plus their directories. **None is an input to the prez binary, so cargo is right and the shim is wrong.** The dep-info files carry 2026-09-14 09:15 local while the binary still carries 2026-09-10: a no-op build ran and relinked nothing. Every source-tree invocation since at least 2026-09-10 08:10 local, when `Cargo.lock` became newer than the binary, has taken this path.

## Root cause: two defects, each sufficient alone

1. **The reference is the older binary** (`b8dc9f1`, ST0017). A workspace build relinks only the binary whose inputs changed, so an edit that feeds one binary leaves the other's mtime behind it for good. The comment at `:159-164` describes this exact loop -- "report stale on every later invocation, rebuild nothing, and announce a rebuild each time" -- and adopts a rule that still produces it: after a showreel-only edit the older binary IS prez, and after a prez-only edit it is showreel, so it loops in both directions.
2. **The walk counts paths that are not compile inputs** (`538e7fe`, issue 0018). The comment at `:122-125` accepts that because over-inclusion "costs one rebuild ... Ruled by vc 2026-09-09." **That premise is false, and the ruling was vc's.** A cargo build with nothing to do never touches the binary, so an over-included path stays newer than the reference forever, and the cost is a rebuild on every run.

The general form: **a staleness predicate needs a fixed point -- once the remedy it triggers succeeds, it must read fresh.** This one has none whenever a walked path is not an input to the older binary.

## Why nothing caught it

`prez.bats` drives the real `prez_is_stale` over fixtures, but the fixture only ever edits a source BOTH binaries are built from (`opt/prez/test/prez.bats:251`), so it never meets a path that feeds one binary or none, and no test states the fixed point. The comment at `prez.bats:243-247` dismisses the symmetric case -- "showreel rebuilt, prez not -- passes either way and so proves nothing" -- and that is the state the real tree is in.

It survived four days of use for a plainer reason: during active development a rebuild notice on every run is what you expect. It only reads as wrong once the sources stop moving.

## Consequences

- **Output is correct.** Cargo confirms the exec'd binary is current.
- **The notice is defeated.** A line that prints on every run stops being read, including the day a real rebuild happens.
- **cargo becomes a runtime dependency of every source-tree run.** A false stale verdict reaches `require_command "cargo"` (`:203`), so a caller without cargo on `PATH` is refused although the binary is fresh. Derived from the code path; not observed.
- **Installs are immune.** Install mode never evaluates staleness (`:185-197`), and neither `b8dc9f1` nor `538e7fe` is in any tag.

## Severity

Medium. Loud rather than silent, and the output is correct, but it defeats the shim's only freshness signal on every source-tree run and makes cargo a hard runtime dependency there. Not higher because installs never reach the path.

## The fix hv ratified, 2026-09-14

hv, answering vc's "proper fix" recommendation in session `1a7ad8f5-667f-4649-8e7f-a75680ab8d13`: "Yes, do that. Route the fix to utilz-cc and do this now inline immediately."

**Measure against a stamp the shim writes, not against the binaries.**

- The shim creates a pending stamp in `$TARGET_DIR` immediately BEFORE `cargo build` starts, and moves it into place only when the build succeeds. Its mtime is the build's START, so an edit made during a build still reads newer afterwards.
- `prez_is_stale` reads stale when either binary is missing, when the stamp is missing, or when any walked path is newer than the stamp.
- The wide walk, the `target/` prune, `-mindepth 1` and the absence of `-type f` stay; each was measured into place. The older-of-two-binaries reference and its comment go.
- A failed build leaves the previous stamp, so the tree stays stale and the next run retries.

This restores the fixed point -- after any successful shim build nothing is newer than the stamp -- and makes the 2026-09-09 ruling's premise true: over-inclusion now costs exactly one rebuild.

Rejected: letting cargo decide on every run (one oracle, but a real rebuild then either shows no progress or prints cargo's `Finished` line every time); parsing cargo's dep-info in bash (a second copy of cargo's own freshness logic).
