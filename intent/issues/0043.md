install_e2e.bats builds its fixture by copying `$UTILZ_HOME/.git` and then the worktree (issue 0042's order). That assumes `.git` is a directory. In a linked worktree (`git worktree add`), `.git` is a one-line FILE, `gitdir: <repo>/.git/worktrees/<name>`, so the copy carries a pointer into the real repository rather than a repository of its own.

OBSERVED 2026-09-21, bats opt/utilz/test in vc's detached worktree at be34adb: `not ok 113 setup_file failed`, at install_e2e.bats:50, `rm: .../e2e-src/.git/index.lock: Not a directory`. The other ten cases in the file never ran. The same file passed 11 of 11 from the primary checkout at the same commit.

WHY IT MATTERS MORE THAN A RED SETUP. The rm failing is what stopped the run. Without it, `fixture_commit "$src"` would have run `git add -A` and `git commit` inside the copy, and git follows the pointer: the fixture's content would be committed into the REAL repository's object store, onto that worktree's HEAD. On a worktree checked out on a branch, that is a commit nobody made, landing on the developer's branch. A test must never write to the repository it tests.

The line at :50 predates 0042 (the cp -a of the whole tree copied the same pointer), so every linked-worktree run of this file has always failed at the same line. Nothing has been written through the pointer.

THE FIX: setup_file refuses by name, before anything is copied, when `$UTILZ_HOME/.git` is not a directory: it says the fixture needs a primary checkout, because a linked worktree's .git is a pointer, and a copy of it would commit into the real repository. The refusal fails the file loudly rather than skipping it, because a skip reads as clean. Making the fixture work from a linked worktree (eg a clone for .git) is not taken: the clone loses the remotes that install_ci_state asks CI through, and that changes what the file tests.
