## What

hv, 19 Oct 2026, to vc: "It can't only depend on macOS. We need to make it work on both Linux and macOS and the bits that can't work as-is outside macOS (ie menubar app) degrade sensibly in non-macOS environments." vc's decision 32 puts it in 2.14.1, owner dc, with the design first.

Utilz is a macOS-only install today, by one line: the formula's `depends_on :macos` (`packaging/homebrew/utilz.rb:17`). Nothing else in the install path assumes macOS: `bin/utilz install --prefix <p> --managed-by brew` builds prez with cargo, copies the owned set with `cp -p` and recreates links with `readlink` and `ln -s` (`opt/utilz/lib/install.sh:517` to `:601`), and its sha256 helper already tries `shasum`, then `sha256sum` (`:58`). CI's Ubuntu job runs 14 utilities' suites on every push (`.github/workflows/tests.yml:102`), and kovacs ran the same loop green at `2d73b7f` (dc's slot 83).

What does not hold on Linux is the part that needs macOS, and how each utility and `utilz doctor` say so:

- **macoz** refuses by name off macOS (`check_macos`, `opt/macoz/macoz:25`, called at `:431`), but before it parses its arguments, so `macoz` with no arguments refuses rather than print its usage. It exits 1, where Utilz's refusals exit 2. Its yaml declares no dependency, though `setpicfor` needs fileicon (`opt/macoz/macoz.yaml:6`).
- **arngz** works on Linux for `list`, `show`, `delete` and `current`. `apply` refuses because `defaults` is missing (`opt/arngz/arngz:985` to `:993`, `:1377`); `diff` and `discover` refuse because `hs` is missing, with the fix `arngz init --yes` (`:789` to `:802`), which cannot work there. `init --yes` refuses for want of Hammerspoon (`:853`); `doctor` runs its seven checks and fails them (`:1647`). No refusal says the verb needs macOS. Every engine verb starts at the engine's observe, which only runs inside Hammerspoon (`opt/arngz/lib/arngz.lua:168` to `:200`); the planner itself is pure Lua (`opt/arngz/lib/plan.lua:3`).
- **menuz** works on Linux for `init`, `use`, `log` and `stamps`. `edit` without `--editor` runs `open -t` unguarded (`opt/menuz/menuz:430`), which is missing there or is another tool. `validate`, `render`, `start` and `restart` refuse for want of an app; `build` and `test` for want of Xcode (`:192` to `:202`). `install` from a keg downloads the app and then fails at `ditto` (`:812`); `uninstall` and `stop` do nothing and exit 0 (`:872`, `:731`); `status` and `doctor` run and fail their lines. None says the verb needs macOS.
- **clipz** works on Linux (`opt/clipz/clipz:25` to `:105`: xclip or xsel under X11, wl-clipboard under Wayland), and its yaml declares none of those tools.
- **prez**'s `present` falls back to `open` when it finds no Chromium-family browser (`opt/prez/crate/src/drive.rs:269`). On Linux that is no opener, or on Debian `openvt`.
- **stampz** hashes with `shasum` alone (`opt/stampz/stampz:505`, `:517`), with no `sha256sum` fallback.
- **utilz doctor** has no notion of a utility's platform. Its `[5/7]` lists every utility (`opt/utilz/lib/common.sh:714` to `:772`), and its `[6/7]` sweeps every utility's dependencies (`:795` to `:932`). On Linux an `app:` dependency (arngz's Hammerspoon) reads as optional, "a macOS app, so never present on Linux" (`:370` to `:380`), followed by `brew install --cask hammerspoon`, a cask brew has only on macOS; arngz's `hs` reads as a plain optional dependency to install. The platform question is asked inline three times: `check_app` (`:346`), `dependency_purpose` (`:376`) and the Xcode block (`:898`), beside clipz's own `detect_platform` (`opt/clipz/clipz:25`) and macoz's `check_macos`.
- **The docs** say nothing of Linux as a platform for Utilz. README's Installation (`README.md:52` to `:62`) is a clone; its "Included Utilities" (`:160`) has one heading per utility and no platform marker; `help/macoz.md:26` alone says it requires macOS.

## Design

dc, 19 Oct 2026, at `ceba425`. Size: L, in three owners' parts. It builds on 0080's `run_doctor` (`:801`) and lands after it.

1. **One answer to "which platform".** `utilz_platform`, in `common.sh`, prints `macos`, `linux` or `other` from `uname -s`, called by name so a test can stub it. `check_app` (`:346`), `dependency_purpose` (`:376`), the Xcode block (`:898`), clipz's `detect_platform` and macoz's guard all ask it, and none asks `uname` itself.
2. **A utility's platforms, declared once, in its yaml.** `platforms: [macos]` names where a utility runs; absent means everywhere. macoz declares `[macos]`. arngz and menuz do not: each runs partly on Linux, and its macOS verbs refuse by name (item 4). A dependency entry takes the same key, and an `app:` entry means `[macos]`; arngz's `hs` declares `[macos]`. macoz gains its fileicon as an optional dependency, and clipz gains `xclip` and `wl-copy` as optional dependencies on `[linux]`, each with its purpose (`xsel` and wl-clipboard named in it).
3. **One refusal, by name.** `refuse_off_macos <what> <needs> [<what works here>]`, in `common.sh`, prints `<what> needs <needs>, so it is not available on <platform>` and, when given, what does work, and exits 2. `require_platform <utility>` reads the utility's `platforms` and refuses through it. macoz's `main` calls `require_platform macoz` after its help arms, in place of `check_macos`, so `macoz --help` and `macoz` with no arguments print usage everywhere, and every verb refuses on Linux, exit 2.
4. **The macOS verbs of arngz and menuz refuse by name, before they call anything.**
   - arngz: `apply`, `diff`, `discover` and `init --yes` call `refuse_off_macos "arngz <verb>" "macOS and Hammerspoon" "arngz list, show, delete and current work here"` first. `doctor` on Linux prints that one line and checks only the catalogue; plain `init` makes the catalogue and drops its Hammerspoon advice.
   - menuz, utilz-ic's to make and to review: `edit` without `--editor`, `validate`, `render`, `build`, `test`, `install`, `uninstall`, `start`, `stop` and `restart` refuse the same way, naming the app or Xcode; `status` and `doctor` print one platform line; `init`, `use`, `log` and `stamps` run as today. menuz's suites keep testing the macOS paths on Linux, as tests.yml's loop does, by stubbing `uname` as Darwin.
5. **utilz doctor says what is not here, and counts nothing for it.** In `[5/7]` a utility whose platforms exclude this one reads `macoz: macOS only, not available on Linux`, and is no issue. `[6/7]` skips that utility's dependencies, and reports a dependency whose platforms exclude this one (arngz's `hs` and Hammerspoon) in one line as macOS only, with no install line. Nothing else in the verdict changes. `help/utilz.md`'s doctor section (`:86`) says so, and drops its claim that the check results go to stderr and only the headers to stdout (`:102`), since `bin/utilz:118` runs `run_doctor 2>&1`.
6. **list and help mark it.** `utilz list` and `utilz help` show `macoz (macOS only)` on Linux.
7. **prez opens with the platform's opener.** When no Chromium-family browser is found, `present` uses `open` on macOS and `xdg-open` elsewhere (`drive.rs:269`), through one small function a unit test pins for both.
8. **stampz shares install's sha256.** `_install_sha256` (`install.sh:58`) moves to `common.sh` as `sha256_of`, and stampz (`:505`, `:517`) and install both call it.
9. **The formula and the docs.**
   - `packaging/homebrew/utilz.rb` drops `depends_on :macos` (`:17`). Its caveats add: "On Linux, macoz and menuz's app need macOS, and arngz's apply, diff and discover need macOS and Hammerspoon; utilz doctor names what this machine lacks." The tap takes it at the cut (vc's todo 43, step 1).
   - README: under Installation, a Platforms paragraph saying Utilz runs on macOS and Linux and what needs macOS; in "Included Utilities", the platform beside macoz, menuz and arngz.
   - `help/macoz.md`, `help/menuz.md` and `help/arngz.md` each carry a Platform line naming what needs macOS.
10. **The tests, red first.** Each runs under a stub `uname` first on PATH, so both platforms are tested on either.
    - `common_lib.bats`: `utilz_platform` for Darwin, Linux and another name; `refuse_off_macos`'s message and its exit 2; `require_platform` against a yaml with and without `platforms`.
    - `macoz.bats`: under Linux, every verb refuses by name with exit 2, and `--help`, `--version` and no arguments print usage.
    - `arngz.bats`: under Linux, `apply`, `diff`, `discover` and `init --yes` refuse by name before any `defaults` or `hs` call (fakes that record calls stay empty).
    - menuz's, by utilz-ic: the same for its macOS verbs.
    - `common_lib.bats`, beside `run_doctor`'s tests (`:307`): under Linux, `[5/7]` reads macoz as not available here, its dependencies are not counted, and arngz's `hs` and Hammerspoon read as macOS only with no install line. Under Darwin, nothing changes.
    - prez: the opener function's unit test.
    - CI: test-linux's roster (`tests.yml:102`) gains cleanz, clipz and macoz, and the comment at `:93`, which left out macoz as macOS-only and clipz as "clipboard unreliable in CI", goes: 0082's stubs answer the second, and macoz's suite now proves the first. cleanz was never on the roster, for no stated reason. clipz runs there with 0082's stubs; macoz's suite proves the refusal.
11. **Runs,** each booked: the new tests red on main's code and then green, under bash 3.2 and bash 5, in a worktree; the estate; shellcheck 0.9.0 on every changed shell file; kovacs's loop with the new roster, and `utilz doctor` from the source tree there, which is the Linux verdict before the cut. After the cut, kovacs-sysadm runs `brew tap`, `brew install utilz` and `utilz doctor` at hv's approval (vc's todo 43, step 4), and that verdict is the one this issue designs.
12. **Versions.** macoz, arngz, clipz, stampz and prez each move by a patch number; menuz's is utilz-ic's to set; utilz's is the framework's `VERSION`, which the cut sets.

**Owners.** dc: items 1 to 3, 5, 6, 8, 9, 10 and 11, and arngz's and macoz's part of 4. utilz-ic: menuz's part of 4 and its tests. prez's item 7 is three lines of Rust, dc's unless vc gives it to utilz-cc.

**Seen, not taken.**

- clipz on X11 with no display fails with xclip's own error (`opt/clipz/clipz:133`). That is xclip's answer, and true.
- pdf2md and xtrct make their venvs beside their libraries (`opt/pdf2md/pdf2md:30`, `opt/xtrct/xtrct:30`), so in a brew install the venv is made inside the keg, on macOS as on Linux. It works there; whether a keg should be written at runtime is a question for its own issue.

### utilz-cc's prez part (items 7, 15 and 16)

cc, 19 Oct 2026, at `bfd86cd`. vc approved it as drafted, the same day. Size: XS.

20. **One function chooses the opener, or refuses.** `open_presenting` (`opt/prez/crate/src/drive.rs:234`) asks `browser::find` once and keeps its refusal: a browser named with `--browser` that is not there is still an error, never a fallback. With no browser named and none found, the refusal goes to `fallback_opener(os, lookup, no_browser)`, which chooses `open` when `os` is `macos` and `xdg-open` otherwise, and looks it up with `lookup`. It returns the opener's name and path, or a `Failure` that keeps the finder's list of every path it probed and adds `and no '<opener>' on PATH to open the deck with`. Its remedy is `install Chrome, Chromium, Edge or Brave, or name one with --browser PATH, or put <opener> on PATH`, and `Failure::new` exits 2 (`crates/artifact/src/failure.rs:21`). The caller passes `std::env::consts::OS` and `artifact::path::on_path`. So the choice is tested for both platforms on either, and no test sets PATH, which the artifact crate's own tests empty while they run (`crates/artifact/src/path.rs:17`). The warning that the window will not be de-chromed prints only once an opener is found, and names it.
21. **What it replaces.** `drive.rs:269` spawns `open` on every platform, so on Linux `present` reaches no opener, or on Debian `openvt` (item 7), and fails at the exec, if at all, with "could not launch 'open'".
22. **The tests, red first,** in `drive.rs`'s own tests. A first build gives `fallback_opener` main's behaviour, `open` everywhere with no lookup, so each test fails at its own assertion, not at the compiler. Then the function is written.
    - It chooses `open` for `macos` and `xdg-open` for `linux` and for another name, each found through a lookup that knows only that name.
    - With a lookup that finds nothing, it refuses with code 2. The message keeps the probed list and names the opener, and the remedy names `--browser PATH`.
23. **Docs and the version.** `help/prez.md:273` says `present` refuses when it finds no browser, which it has never done: it falls back to the opener. The paragraph says what `present` does instead, and when it refuses. prez moves to 2.5.2 (`crate/Cargo.toml` and `Cargo.lock`), its second patch since 2.14.0, as menuz moved twice. One CHANGELOG line goes under Fixed.
