## What

utilz-ic, 23 Oct 2026, reading `bin/devbin macos` before hv's post-cut steps for 2.14.2. vc read the same code and agreed that day, and gave the fix to utilz-ic, to ride the next release.

A release's `Menuz.app.zip` carries the build stamps of whatever tree `app-sign` ran in. `app-sign` builds HEAD, whatever commit that is. `publish` checks only the bundle's id and version. So a Menuz.app built from a commit other than the release tag's can ship as that release's asset, and nothing refuses it: not `app-sign`, `app-notarize` or `publish`, and not a Homebrew install's `menuz install`. In every Homebrew install, the menu's top row then names that commit and the kind `dev`, and the bundle can carry code that is not the tag's.

## Measured

23 Oct 2026, after 2.14.2's cut (tag `2.14.2` on `54b6262d`).

- `cmd_app_sign` (`bin/.devbin/cmd/macos:373` to `:405`) builds through `"$ROOT/bin/utilz" menuz build --release`. It reads nothing of HEAD or the tag. `ROOT` is the tree the script sits in (`bin/devbin:45`).
- menuz stamps a build from HEAD (`opt/menuz/menuz:569` to `:606`), and the bundle carries the stamps as `MenuzCommit`, `CFBundleVersion` and `MenuzKind`:
  - `MENUZ_COMMIT` is HEAD's first eight characters, and `MENUZ_BUILD` is HEAD's commit count.
  - `MENUZ_KIND` is `release` only when `git tag --points-at HEAD` names the root `VERSION`'s tag and the source stamp is clean. Otherwise it is `dev`.
- `app_ship_blockers` (`cmd/macos:333` to `:342`) reads only `CFBundleIdentifier`, and `CFBundleShortVersionString` against `opt/menuz/VERSION`. It is the one check `publish` runs on the bundle itself, on the staged copy (`:488`) and again on the copy unpacked from the zip (`:507`).
- A Homebrew install's `fetch_asset` (`opt/menuz/menuz:826` to `:866`) checks the asset's signature, `spctl`'s `source=Notarized Developer ID`, its bundle id and its version. It checks nothing of its kind or its commit.
- When ic read it after the cut, main's HEAD was `4e6dd63b`, five whiteboard commits past the tag, and `git tag --points-at HEAD` printed nothing.
  - An `app-sign` in the primary would have built menuz 0.4.7 as build 1692 with `MenuzCommit 4e6dd63b` and `MenuzKind dev`, where the tag's build is 1687, `54b6262d`, `release`.
  - `publish` would have taken it, since its version is 0.4.7.
- `help/menuz.md:264` says the signed release asset is built at the tag from a clean tree, so a Homebrew install's app shows the release form. `docs/releasing.md:70` has hv run the three steps "at the tag". Nothing checks either.
- No asset built off its tag has shipped:
  - 2.14.1's `Menuz.app.zip` reads 0.4.5, build 1425, `MenuzCommit 43fca620`, `MenuzKind release`.
  - 2.14.0's reads 0.1.0, build 1214, `069e0f38`, `release`.
  - Each is its tag's commit and count.
  - 2.14.2's was built from a detached worktree at the tag (vc's `~/Devel/scratch/utilz-vc/wt-2142`), on vc's word.

## Fix

1. `publish` refuses a bundle, uploading nothing, when its `MenuzKind` is not `release`, or its `MenuzCommit` is not the first eight characters of the commit the root `VERSION`'s tag names. It checks the staged bundle and the bundle unpacked from the zip, as it refuses a wrong version today. Each refusal names the value it read and the one it wanted. A tag that does not exist in the tree is refused by name.
2. `app-sign` refuses before any build when HEAD does not carry the root `VERSION`'s tag. The refusal names HEAD, the tag and the commit the tag names, so the build and the signing are never spent on a bundle `publish` would refuse. Whether `app-sign` refuses or only warns is for vc's read of the design.
3. `docs/releasing.md`'s "After every cut, at the tag" says how to run the three steps: in a tree whose HEAD is the tag, which is a detached worktree once main has moved past it. It also says `app-sign` and `publish` refuse otherwise. `bin/devbin macos`'s own help names the new refusals.
4. Tests in `opt/menuz/test/macos.bats` sit beside `publish`'s refusals. A bundle stamped `dev`, and one whose commit is not the tag's, are each refused with nothing uploaded. `app-sign` refuses off the tag before any build. The existing pass case is stamped as the tag's build.
5. Not here unless vc's read adds it: `menuz install` refusing an asset whose `MenuzKind` is not `release`, as a check a Homebrew install makes for itself.
